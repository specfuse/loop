## [Unreleased]

### Added

- **`specfuse-agent`, a new console script — the operator-launched conductor that drives a specfuse-configured repository to drain.** `specfuse-agent = "specfuse.agent.run:main"` takes the shipped entry points from five to six. It acquires its own `.specfuse/.agent.lock` — **distinct from the driver's `.specfuse/.loop.lock`**, so an agent run and a `specfuse run` do not deadlock each other, and exactly one agent may run per repository — reads repo state into one pass, then runs select→execute→reconcile until the work drains or a cap fires. Six action providers register by default when `--repo` is given: answered escalations, bugs, features, triage, findings-diagnose and findings-autofix. **Stale-lock detection and PID files are deliberately not built**: the kernel releases a `flock` on process death including SIGKILL, so there is no stale state to detect. **Selection has been exercised against live repository state; execution has not.** A read-only probe built a real snapshot of this repository (36 issues, 1 PR, 63 feature folders), all six providers advertised without error, and the selector ranked and chose correctly under `rules.bugs.preempt` — but **no item was ever executed**, so `execute()`, the driver invocation, every halt classification and every escalation path are proven only by test against injected runners and fixture feature folders. **The first real run is still ahead of this command**; treat its execution half as unproven, not as broken (FEAT-2026-0049)
- **Seven CLI flags on `specfuse-agent run`, all optional with safe defaults:** `--repo` (OWNER/NAME), `--policy` (path to `agent-policy.yml`), `--features-root` (path to `.specfuse/features`), `--monitoring-config` (defaults to `.specfuse/monitoring.yml`), and three caps — `--max-minutes`, `--max-tokens`, `--max-items` — each defaulting to `None` meaning unbounded. Two cap semantics a reader will otherwise assume wrongly. **Caps are checked at item boundaries only and never interrupt a running item**, so `--max-minutes 30` against a two-hour item stops at two hours; that overshoot is deliberate, traded against the alternative of a killed-mid-work-unit driver state whose cheapest known recovery is to discard the work. And **`--max-items` counts advertised items, which for a feature means gates, not features** — one feature advancing four gates consumes four items, so `--max-items 3` yields one feature, not three. **`--max-tokens` is wired end to end and cannot currently fire**: `ActionOutcome.spend` defaults to zero and no provider assigns it, so the ledger is live and the number flowing through it is always zero. Treat the flag as declared-but-inert until a provider reports real spend (FEAT-2026-0049)
- **`rules.features.wip_limit` and `rules.features.gate_review` in `.specfuse/agent-policy.yml` become load-bearing — both have been validated since FEAT-2026-0044 and read by no shipped code until now, so an operator who set them expecting no effect will now get one.** `wip_limit` (int ≥ 1, default `1`) caps how many distinct features one run advances, taken in `queue:` order, with already-`done` entries consuming no slot. `gate_review` (`human` | `auto`, default `human`, with an optional per-feature `overrides` map) decides what an `awaiting_review` halt does: under `human` the run files a `gate-review` needs-human issue and switches to the next workable entry; under `auto` it records the halt in the run summary and **files nothing**, because the agent cannot arm a gate — arming stays `/arm-gate`'s job — and filing nothing is the only honest `auto` behaviour. An absent policy file, an absent key, or a wrong-typed value resolves to the conservative default rather than raising (FEAT-2026-0049)
- **Two escalation categories reach GitHub for the first time: `drafting-needed` and `gate-review`.** Both have been declared in `escalation.py`'s `CATEGORY_LABELS` since that module shipped and used by nothing; the feature provider is their first consumer, so repositories will begin seeing needs-human issues carrying those labels. No category was minted and the registry is unchanged. A queue entry with no feature folder escalates as `drafting-needed` and **reaches no driver invocation at all** — drafting stays human in v1, and async drafting is FEAT-2026-0050 (FEAT-2026-0049)

### Changed

- **`specfuse-agent run` now logs what it is doing while it does it, in the same timestamped shape `specfuse run` uses.** The command printed nothing between launch and its final summary: the first live run was **85 minutes of silence**, so an operator watching had no way to distinguish a working item from a hung one, no per-item cost, and no record of what the snapshot had even offered. It now emits `[HH:MM:SS] <event>` lines — matching the driver's per-work-unit line so one operator reads both the same way — for the run start, the snapshot's own counts (issues, PRs, features, queue depth, and any section that failed to read), each item **before** it is executed with its id/kind/provider/summary, and each result with its wall-clock cost and outcome. `run_agent` gains an optional `reporter` parameter; `None` prints, and passing a collector silences stdout entirely, which is what the tests do (FEAT-2026-0049)
- **An unattended `specfuse-agent run` now dispatches the loop driver against the `queue:` top — a change to what an existing command does, with no opt-in flag.** Before this, the command could file bug PRs, triage issues, answer escalations, post diagnoses and fire autofixes. After it, the same command reads `queue:` from `.specfuse/agent-policy.yml`, classifies the top entry, and invokes `specfuse run` on the first workable feature — **which commits**. This is the largest expansion of what an unattended run can do, and there is no flag to disable it: the feature provider is registered in `default_providers()` like the other five, on the grounds that the approved roadmap goal funds exactly this behaviour and requiring a flag would contradict it rather than narrow it. The blast radius is bounded by machinery already shipped and tested — the agent lock, the item-boundary caps, and the PAUSE marker checked each iteration. **Two things to know before the first run.** The driver is invoked as a **subprocess**, never imported in-process, and a structural test now enforces that; the consequence is that `specfuse run` resolves `specfuse.loop` from the *installed* suite rather than from a working tree, which is correct for every target project and surprising only in a checkout of this repository. And the decision to ship without an opt-in flag was **made by the agent overnight under a standing authorization to arm unattended, with no operator review** — see `GATE-04-REVIEW.md` OQ-3, which recommends the operator review this specific call before merge (FEAT-2026-0049)

### Fixed

- **`JUDGE_PATHS` no longer treats every file under `specfuse/loop/` as a judge surface — the blanket prefix is replaced by a named registry of the modules a verdict actually reads.** The prefix was right in intent and far too wide in reach: it covered all 44 modules of the driver package plus every shipped document, so **in the one repository where it applies — this one — no gate shipping documentation could arm, and no bug fix touching any driver module could auto-merge**, whether or not it went near a decision. FEAT-2026-0053's close recorded the first half as a structural limit making `auto` "currently unreachable for a large class of features", and said narrowing it "needs a decision with evidence, not a one-line prefix edit"; the first unattended agent run hit the second half, declining two of eight items `judge_path_touched`. `JUDGE_MODULES` now names the **24** modules a merge/arm/close verdict — or the evidence a verdict reads — depends on (the predicates, the dials and budgets, what a WU or close must satisfy, the driver's own guards, event-trail validation, and the evidence pipes a verdict reads *through* -- `_miniyaml`, `_wu_sections`, `triage.parse_marker` and `rearm_migration`, none of which signs a verdict and each of which can change one), and `JUDGE_DATA_PREFIXES` names the package-data subtrees that seed a judge surface downstream (`rules/`, `rules-local/`, `schemas/`, `templates/`, `workflows/`, `verification.yml.example`). **`specfuse/loop/data/docs/` is the one deliberate exclusion**, on the evidence that no predicate reads it — that mirror is why any documentation-shipping gate fired the class. The five universal surfaces (`.specfuse/verification.yml`, `.specfuse/hooks/`, `.specfuse/rules/`, `.github/workflows/`, `pyproject.toml`) are unchanged, and they are the only entries that match in a project that installed Specfuse rather than holding its source. **An allowlist stops protecting the moment someone forgets to extend it, which the blanket prefix could not do**, so the narrowing ships with the counterweight that makes it safe: `NON_JUDGE_MODULES` / `NON_JUDGE_DATA_ENTRIES` record every unlisted file with a written reason, and `tests/test_judge_path_registry.py` enumerates `specfuse/loop/*.py` and the data tree and **fails when anything appears in neither** — a new decision module cannot escape by omission, it has to be classified. Same shape as the `DEPENDENCY_MANIFEST_COVERED` / `_NAMED_UNCOVERED` pair alongside it. **This widens what may proceed without a human**: a PR editing a driver module outside the 20 is now eligible to auto-merge where it previously was not (#1938)
- **An escalation about a GitHub issue is now recorded on that issue, not filed as a new one — the agent no longer answers a halt by creating a second issue for a human to correlate back by hand.** A new `escalation.annotate_escalation` posts the same conforming six-part body as a **comment** on the issue the halt is about, labels it `needs-human` + the category, and assigns the operator; `EscalationPayload` gains `target_issue`, and `specfuse.agent.run` routes on it — set, it annotates; unset (a gate review, an unplaceable queue entry, work that is about no issue), it still files through `emit_escalation`, which is unchanged. The comment is idempotent on the correlation marker and the label/assignee write is re-asserted every time, so a first call whose label failed is repaired rather than left half-applied; labelling is best-effort and never raises, per #1785's rule that losing a projection must not lose the record. **`bug_lane_run` now files nothing at all** — the lane returns a verdict, and recording it belongs to the caller that knows the issue. Measured on the first unattended run: **eight halted items produced eight new issues**, each saying "issue #N's PR was declined" from a fresh issue number, and issue #1183 alone accumulated three of them across three runs. Two of those tracking issues were then triaged `bug` themselves, which — with the selection fix below — is what turned an escalation into the next run's work item (FEAT-2026-0049)
- **`rules.bugs.automerge: "off"` is no longer reported as a guardrail decline.** The lane's merge branch is `if dial and decision.eligible:`, and everything falling past it returned `OUTCOME_DECLINED` carrying whatever reason the guardrails produced — including `eligible`. With the dial off, a PR that passed **every** guardrail was reported as "declined by the merge guardrails -- `eligible`", under a body whose "why it did not close automatically" section read "the merge guardrails declined the PR". Both halves were false: nothing declined, and the guardrails were the one thing that had passed. Observed live on issue #296. A new `OUTCOME_AUTOMERGE_OFF` now carries that case, with its own escalation body naming the dial as the only thing in the way, categorised `merge-approval` rather than `blocked-wu`, and no decline label written to the PR (there is no declining reason to project). **This is a new value in a public outcome set**: a consumer matching on `OUTCOME_DECLINED` to mean "did not merge" will now miss this case (FEAT-2026-0049)
- **The bug lane no longer waits up to ten minutes for CI before checking guardrails that CI cannot affect.** `run_bug_lane` read `pr_ci_conclusion` — which polls for `CI_WAIT_SECONDS`, 600 — before evaluating anything else, so a PR touching a judge path, or over the diff cap, or with no test evidence, paid the full wait to be declined for a reason that was decidable from the PR's own file list the moment it opened. A new `bug_lane.evaluate_pr_shape_guardrails` holds exactly the checks needing no CI and no cap read, and the lane runs it first: a shape decline now costs **zero** `gh pr checks` calls (verified by call count, 1 → 0). `evaluate_merge_guardrails` is composed from the same predicate with the CI check kept in its original position, so **no declining reason changes precedence** and it remains the single predicate the merge decision reads. Two of eight items in the first unattended run paid the wait to be declined `judge_path_touched`. **Not fixed, and worth stating plainly: judge-path membership cannot be known before the fix exists**, since it is a property of the diff — the saving here is the CI wait, not the fix itself. In a repository where `specfuse/loop/` is both a judge path and where most bugs live, most bug-lane PRs remain structurally unmergeable by design (FEAT-2026-0049)
- **A declining guardrail now reports the measurement behind it, not just its name.** `BugLaneResult` gains `evidence`, rendered into the escalation body: `judge_path_touched` names **which** paths (`_touches_judge_path` became the public, path-returning `judge_paths_touched`), `diff_too_large` names the line count and the cap it exceeded, `no_test_evidence` names the declared test paths nothing matched. Every escalation the first unattended run produced was the reason constant and nothing else, so the reader had to open the diff and re-derive what the lane had already computed (FEAT-2026-0049)
- **The run summary no longer claims an escalation went unfiled when it was filed.** `bugs.py` returned `escalation=None` for the two outcomes the lane filed for itself, and the loop printed `(summary only, no issue filed)` for exactly that case — so four items of the first live run reported no trace while issues #1873, #1878, #1879 and #1880 existed, and an operator reading the summary would reasonably conclude the work was lost. Nothing sets `escalation=None` for a recorded escalation any more; the line now reads `(recorded on issue #N)` or `(filed as issue N)`, and the no-trace wording is reachable only when nothing recorded anything and no longer asserts anything about issues (FEAT-2026-0049)
- **The bugs provider no longer re-advertises work a human or an open PR already owns.** Two exclusions in `BugsProvider.advertise`. An issue labelled `needs-human` or `blocked-wu` is parked awaiting a decision, so re-running the lane against it can only repeat the outcome that parked it — issue #1183 was refused on three separate runs. **More seriously, every escalation the agent filed was itself triaged `bug`**, so the next run's candidate list contained the agent's own "PR was declined by the merge guardrails" reports, with nothing in selection to stop the lane trying to fix them. And an issue already cited by an open PR's `closes #<n>` line has a fix awaiting review; re-fixing it opens a second PR for the same bug, which issue #1163 did while PR #1876 was open. `_read_prs` now requests the PR `body` so the second exclusion is readable from the snapshot at all — the same `closes #<n>` linkage `_find_pr_for_issue` already relies on (FEAT-2026-0049)
- **The `preexisting_gate_failure` escalation no longer claims a feature's tree "matches its integration branch" while its own diffstat lists changed files.** A fresh gate almost always has a non-empty `git diff <base>...HEAD --stat` — the feature's own plan/scaffold files — so the header contradicted the evidence printed directly beneath it. The header now states what the diffstat actually proves: the failing check's input files are unchanged, not that the tree is unchanged (#240)
- **A `produces:` entry mixing a literal `[id]` segment with a wildcard elsewhere now matches, in both guards.** #1181 made a bare bracketed path literal, but `src/app/[id]/*.ts` still failed: the wildcard makes the whole entry a pattern, so `[id]` recovers its character-class meaning and matches nothing — `glob.glob` returned `[]` with both files present, and `fnmatch` failed identically. **Unlike #1181, both halves of the unified contract missed this one**: the diff check's literal-equality branch rescued a bare bracketed path, but an entry carrying a wildcard is never literally equal to a touched path, so it fell through to `fnmatch`. A new `produces_glob_pattern()` escapes bracket segments that carry no wildcard **of their own**, applied at all three sites — the presence gate, #1412's refusal note, and `assert_produces_in_diff`. Escaping is per **segment**, so a class written in the same segment as a wildcard (`src/[abc]*.ts`) is left alone and keeps matching as a class: the escape hatch #1181 deliberately preserved for an author who wants a real one. Paths with no bracket are returned unchanged (#1589)
- **A `produces:` entry containing `**` can now match.** `assert_declared_deliverables` called `glob.glob(path)` without `recursive=True`, which makes Python treat `**` as a single `*`: it matches one path level, yields directories for a tree, and the guard's `Path(m).is_file()` filter drops every one of them. A work unit that had produced **every** declared deliverable was refused `deliverable_missing`, retried to the attempt cap, and escalated `spinning_detected` — one downstream occurrence burned **$32.74 across three byte-identical refusals** while `files_touched` contained the files the whole time. Both call sites now pass `recursive=True`: the presence gate and #1412's refusal note, which globs the same patterns and would otherwise report a satisfied `**` entry as `ABSENT`. **Single-`*` behaviour is unchanged** — `src/*.ts` still does not reach into `src/one/`. This is the third instance of the two halves of the unified literal/glob contract disagreeing (after #1181 and #1589): `assert_produces_in_diff` matches with `fnmatch`, whose `*` already crosses `/`, so the diff cross-check accepted the same entry the presence gate refused (#1744)
- **The bug lane can read CI at all, for the first time — `rules.bugs.automerge` has never been able to fire until now.** `pr_ci_conclusion` asked `gh pr checks` for a `--json conclusion` field that **does not exist**: the command exits 1 with `Unknown JSON field: "conclusion"`, so the function returned `unknown` on every pull request — green, red, pending, settled — and `evaluate_merge_guardrails` declined every time. Observed live: PR #1810 was green and `MERGEABLE` and was declined `ci_not_green` anyway, as was #1824. It now reads **`bucket`**, gh's own normalisation across check providers (`pass` / `fail` / `pending` / `skipping` / `cancel`), and maps it: all `pass` or `skipping` is success — **a skipped check is not a failure**, and a required check that did not need to run must not block a merge forever — any `pending` waits, anything else declines. Two further corrections that were wrong independently of the field name: **a non-zero exit no longer means unreadable**, because `gh pr checks` exits non-zero when checks are *failing* (1) or partly skipped (8) as well as when the invocation is bad, so the output is now the authority and the exit code only a fallback; and **an empty row list is treated as pending, not unreadable**, since a brand-new PR has no checks registered yet. This supersedes the diagnosis in the previous entry: the polling added there was real but could not have helped, because it polled a command that failed on argument parsing. `tests/test_pr_checks_json_field.py` now compares the requested field names against the installed `gh` binary's own advertised list — the check whose absence let a field that never existed survive since the lane shipped (#1826)
- **A guardrail label the repository does not have no longer destroys the bug lane's work.** `run_bug_lane` wrote its declining reason as a PR label with `check=True`, so a label that is registered in `LABEL_REGISTRY` but never created on the repository raised `CalledProcessError` out of the lane. Observed live: **29.8 minutes of correct work — a test-first fix and a mergeable PR — discarded at the last step**, with the guardrail verdict replaced by an exception repr, so the operator learned that a `gh` command failed and never learned why the lane declined to merge. Eight of the registry's twenty-one labels were absent; the registry was complete and nothing had ever provisioned them. **The reason is the verdict; the label is only a projection of it**, so losing the projection must no longer lose the item. A new `bug_lane_run.add_guardrail_label` never raises: it attempts the write, and on failure provisions the label on demand via the idempotent `provision_labels` and retries **exactly once**. A label that already exists still costs one call and no provisioning, so the happy path is unchanged. `BugLaneResult` gains `label_written: bool = True` — defaulted, so existing callers are unaffected — which **mirrors `apply_triage`'s `label_written` row exactly**: that consumer already treated the same condition as best-effort, and two consumers of one registry disagreeing about whether a missing label is survivable was the deeper defect (#1785)
- **The bug lane now waits for CI to reach a conclusion before judging it, so `rules.bugs.automerge` can fire at all.** `run_bug_lane` read a pull request's CI conclusion moments after `/fix-bug` opened that PR — `_find_pr_for_issue` then `pr_ci_conclusion`, back to back. A PR seconds old always has queued or in-progress checks, so the single `gh pr checks` read found no conclusion, `evaluate_merge_guardrails` failed closed, and the lane declined. **The dial was therefore structurally unreachable**: an operator setting `automerge: "on"` would get no merges and a stream of `bug-lane:ci-not-green` labels on green pull requests, and would reasonably conclude the guardrails were doing their job when they had never evaluated a real answer. Observed live — PR #1784 was labelled `ci-not-green` while its checks were `SUCCESS` and it was `MERGEABLE`. `pr_ci_conclusion` now polls until every check has a conclusion or a **10-minute** deadline expires (`CI_WAIT_SECONDS` / `CI_POLL_SECONDS`; `sleep`, `clock`, the deadline and the interval are all injectable), and distinguishes **"CI has not finished"** from **"CI finished and was not green"** — a distinction the single read could not draw and the reason it mislabelled. **A settled PR still costs exactly one call**, so nothing pays for the wait unless there is something to wait for, and the fail-closed contract is unchanged: an untrustworthy read, disagreeing conclusions, or checks still pending at the deadline all still yield `unknown`, which is never `success`. A pending-at-deadline result is deliberately reported as `unknown` rather than a new guardrail reason, because a new reason needs a new label and unprovisioned labels are already fatal to this lane (#1785) (#1786)
- **A bare `specfuse-agent run` no longer dies before it selects anything.** With `--features-root` omitted — the default invocation — `FeatureProvider` fell back to the string literal `".specfuse/features"` while `specfuse.agent.state.read_feature_summaries` called `.is_dir()` on whatever it was handed, so `advertise()` raised `AttributeError: 'str' object has no attribute 'is_dir'`. The blast radius was the whole run, not the one provider: `_select_next` iterates every provider's `advertise` with **no per-provider guard**, so the exception propagated out of selection and ended the run, taking the healthy bugs, triage, answered-escalation and findings providers with it. **Every shipped behaviour of the command was reachable only by passing `--features-root` explicitly.** `read_feature_summaries` now normalises its argument at the boundary, so it accepts a `str` or a `Path` and returns an empty result for an absent directory rather than raising — a compatible widening of a public name. The reason no test caught it is worth stating: every existing test injected a fixture `Path`, so the shipped default was the one input never supplied; the new tests exercise the **default** rather than a supplied value, including a `default_providers()`-wide advertise sweep and a `_select_next` survival check. **Not fixed, and still reachable:** the un-guarded `advertise` loop itself, and the equally un-guarded `provider.reconcile()` call — a future provider that raises for a different reason will still end the run (#1746)
- **A deliverable-presence refusal now leaves a diagnostic attempt note instead of a single line the retry prompt already printed.** When a work unit failed the `produces:` presence gate, `work/<WU>/attempt-N.md` held only `assert_declared_deliverables`' one-line summary — the same string the next attempt is handed as its retry reason. Nothing said **which** of several declared deliverables had landed and which had not, so an attempt that wrote one of its two declared files left no record of that, and a real run spent **$3.88 across three attempts** each reaching the same wall with none of it recorded. The note now renders every declared `produces:` entry marked `PRESENT` (with its size, or match count for a glob) or `ABSENT` (no such file / exists but empty / glob matched nothing) as measured on disk, plus the paths the attempt's squash actually touched — with an empty list stated explicitly, since "the agent wrote nothing" is itself evidence. It is composed **before** the rollback: after the reset the squash is gone and every declared path would read `ABSENT`, losing the one distinction the note exists to record. Separately, `persist_attempt_notes` now terminates the last line of every note it writes. **This is why the issue reported a 0-byte file**: the note carried 43 bytes with no trailing newline, and `wc -l` counts newlines, so it read as `0`. Not included, because it needs a change to `execute_unit_attempt`'s return contract rather than a bug fix: the agent's own final message, which the issue also asked for (#1412)
- **A `produces:` path containing a literal `[...]` segment is no longer misread as a glob character class.** `assert_declared_deliverables` classified an entry as a glob whenever it contained any of `*`, `?`, `[`. Every file-based routing convention — Next.js App Router, Remix, SvelteKit — spells a dynamic route segment as a literal `[id]` directory on disk, but to `glob`/`fnmatch` that is a character class meaning "one character, `i` or `d`", so `glob.glob('src/app/api/jobs/[id]/approve/route.ts')` returned `[]` **however the file was actually spelled on disk**. The presence gate refused the work unit on every attempt with a byte-identical error and spun it to `spinning_detected`, burning three dispatches on a check that could never pass. There was no workaround inside the frontmatter contract: the only escape was to stop declaring the path in `produces:` at all. A new `produces_is_glob()` predicate now reads **`*` and `?` only** — `[` is deliberately excluded — and both the presence gate and its docstring read that one rule. This also closes a real asymmetry between the two halves of the unified literal/glob contract: `assert_produces_in_diff` tests literal equality *before* falling back to `fnmatch`, so a bracketed path already satisfied the diff cross-check while failing the presence gate. **Glob behaviour is otherwise unchanged** — an entry carrying a wildcard is still a pattern, so `src/[abc]*.ts` keeps its character-class meaning for an author who wants one. Not fixed: an entry mixing a literal bracket segment with a wildcard elsewhere (`src/app/[id]/*.ts`) is still read as a class (#1181)
- **A closing work unit running under `autonomy_default: auto` no longer has to claim "nothing generalizes" when its lessons do.** `close-b` (`assert_learnings_appended_or_noop`) accepted exactly two things: added lines in `.specfuse/LEARNINGS.md`, or the literal phrase `nothing generalizes` in `RETROSPECTIVE.md`. But `close-i` (`assert_learnings_staged_under_auto`) **forbids** touching `.specfuse/LEARNINGS.md` under `auto`, routing lessons to the feature-local `LEARNINGS-pending.md` instead — so under `auto` the append route was closed and the phrase was the only one left, **including when the session's lessons genuinely generalized**. Six features in one repository staged entries this way, each leaving a retrospective that told the PR reviewer there was nothing to promote while a populated `LEARNINGS-pending.md` sat beside it. `close-b` and `close-intermediate-b` now accept added lines in the feature-local `LEARNINGS-pending.md` as the same evidence, **but only under `autonomy_default: auto`** — outside it `close-i` is inert, `.specfuse/LEARNINGS.md` remains the sanctioned home, and staging alone still refuses, so the guard is not weakened for `review` or `supervised` features. Both enforcement surfaces move together: the post-squash driver guard and the pre-squash `specfuse lint --closing` mirror, which would otherwise keep prescribing the false phrase for cents-cheap in-session feedback. The genuine no-op route is untouched — a session that really found nothing generalizable still writes the phrase (#1419)
- **`specfuse run` now refuses to start when a dispatched session could not create its own session directory.** A run launched from a sandboxed shell whose deny-list covers `~/.claude/session-env` dispatched anyway: the parent process has a working shell, so nothing looked wrong, but every `claude -p` session it spawned failed with `EPERM ... mkdir '.../session-env/<session-id>'` and started with a **dead Bash tool** for the whole attempt. The agent could still use Write, so `files_touched` came back non-empty and the failure read as ordinary work-unit trouble — blame landing on the work unit rather than the environment. Observed cost before this guard: **$7.85 across two attempts**, the second of which correctly diagnosed the EPERM itself and reported `blocked`. `require_session_env_writable` now probes the root with a create-and-remove before any dispatch, in the same preflight block as the existing feature-folder guards, and refuses with the path and the likely cause named. An absent root is **created**, not refused — a first-ever run has no session-env directory, and treating that as failure would halt every clean machine (#1414)

### Breaking

### Breaking

- **`specfuse-lint --closing` gains a new blocking finding, `close-l` (terminal closes) / `close-intermediate-f` (intermediate ones).** A close whose gate carries a `GATE-NN-CRITERIA.md` now fails the closing lint once per untrustworthy entry: a `kind:` missing or outside `criteria_state.ORACLE_KINDS`, a `state:` missing or outside `criteria_state.CRITERION_STATES`, or an entry whose oracle has no knowable scope (`kind: broad`) reading `state: pass` with an `attempt:` that is not the current one — a broad oracle's green can never be carried forward. A `narrow` entry's `pass` from a prior attempt is deliberately not a finding; that carry-forward is the point. The requirement is declared in `closing_requirements.py` and gated on `applies_when: criteria_artifact_present`, so a feature with no artifact lints exactly as it did before — but the driver now seeds that artifact on every close dispatch, so the gate opens as soon as a driver carrying this change is running, and from that point a close session must record a `kind:` and a `state:` for every acceptance criterion in its gate or its closing lint is red. Nothing in this change fills those entries in; that is the close session's own work (FEAT-2026-0056)
- **The driver can now stop a run mid-gate, and it exits with a new status code, `3`.** When a work unit's squash commit touches the driver's own importable surface (a `.py` file under `specfuse/loop/`, excluding `specfuse/loop/data/`) and the gate still has work units pending, the driver halts before dispatching the next one instead of dispatching into a process whose `sys.modules` holds the pre-edit code. **Any downstream project whose gate edits the driver now needs two invocations where one used to complete the gate**, and any script, CI job, wrapper or scheduler reading the driver's exit status sees a value that did not exist before — `0`, `1` (budget and escalation halts) and `2` (unarmed drafts) were the whole vocabulary, and a caller treating "non-zero" as "failed" will report a failure for a run that stopped deliberately and lost nothing. **Nothing is lost and nothing needs repairing:** the halt flips no gate status and no work-unit status, so the gate stays `open`, every remaining unit stays `pending`, and the unit that triggered it is already `done` with its `task_completed` event written. The message names the offending unit, every driver path it touched, every work unit left pending, and the exact command to resume with; stop the driver, start a fresh process, re-run that command, and the run picks up at the unit it was about to dispatch. Expect it once per driver-editing gate. A `--dry-run` never halts, and a driver edit by the gate's *final* unit never halts because nothing is left to dispatch.
