# Changelog

All notable changes to this project are documented here, in the
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) shape: an
`Unreleased` section collects entries as work lands, and each release heading
stamps a version and a date once one is cut.

Every entry is classified `added` / `changed` / `fixed` / or `breaking`, and
carries a `FEAT-YYYY-NNNN` or `#<issue-number>` trace back to the
retrospective or issue that explains it. `specfuse/loop/changelog.py` parses
this document against that schema; it is not free-form prose.

## [Unreleased]

### Added

- **A promotion ledger for triaged feature requests, so the backlog can be counted.** `triage.py` has routed a `feature` decision to `roadmap-add` since it shipped, and nothing ever recorded when a human walked that route — so a triaged feature issue had one observable state forever after: labelled, open, and indistinguishable from every other one whether or not its work was already on the roadmap. "How many feature requests still need a roadmap decision" was unanswerable, so it went unasked, and fourteen accumulated with nobody able to say which were live. `specfuse.loop.promotion` adds the missing state on `triage.py`'s own terms — a body marker is authoritative, `gh` reached through an injected runner, filtering client-side — with `list_unpromoted` / `list_promoted` partitioning the labelled set and `record_promotion` writing the link back to the allocated `FEAT-YYYY-NNNN`. A malformed ID is refused at render time rather than becoming a permanent broken link that reads as a valid one, and an already-recorded promotion is never silently repointed, since rewriting the marker would erase the only record of where the work went. `/attention` closes with the count and the oldest few, below the priority list because standing backlog blocks nothing, and says so explicitly when `gh` was unreachable rather than reporting a confident zero. **Deliberately not the adoption path**: `gh_features.list_features` feeds `/adopt-feature` and requires an allocated ID in the issue *title*, which no inbound request has — measured, none of the fifteen open `triage:feature` issues here would survive that filter, including the two whose titles only look tagged. Allocating the ID is `roadmap-add`'s job, which is where triage already routes them. A `python3 -m specfuse.loop.promotion` CLI is the reachable write path, so the ledger is populated before any skill calls it rather than being a mechanism nothing invokes (#2793)

### Fixed

- **CHANGELOG headings named umbrella versions that were never released.** `## [X.Y.Z+umbrella.A.B.C]` was true for ten releases and then silently was not: `0.13.0+umbrella.0.13.0` and `0.14.0+umbrella.0.14.0` both name an umbrella that was never published. `--umbrella-version` was checked for non-emptiness and nothing else, so a fiction and a fact were indistinguishable to the tool. The requirement's rationale -- "a driver version nobody can install is not a release" -- expired at umbrella 0.11.0, when components became hard dependencies and `pipx upgrade specfuse` began re-resolving on its own; the coordinate became a record of what was current, and a record nobody checked. It is now **resolved from PyPI rather than asserted**: omitted, the latest released umbrella is used; passed, it is validated against the index and a version that does not exist is refused before any file is written, naming what does. An unreachable index does not block a release -- it falls back to an explicitly passed value flagged unverified, because refusing to cut a release over a documentation field is a worse failure than the one this fixes -- but "could not look" is kept distinct from "not there", since conflating them is how a check reports a wrong answer instead of no answer. `main()` takes an injectable `fetch`, so the suite acquires no live dependency on the index (#2757)

- **Nothing stopped an entry being appended to an already-published CHANGELOG section.** Five `fixed` entries were written into `[0.13.0+umbrella.0.13.0]` days after that release was cut, so for a week the published notes described five fixes the tag did not contain while `Unreleased` understated the next release by more than half. `parse_changelog` could not catch it and never could: it validates **shape** -- heading form, the four entry classes, a trace on every entry -- and all five entries were perfectly well-formed. They were in the wrong section, and section membership is not a property of one document; it exists only as a difference between two. `released_section_drift(base, head)` compares each dated section's **set of traces**, and a CI job runs it against the pull request's base. **Adding or removing is refused; editing is not** -- that was the open question at filing, and a byte-level freeze would have forbidden the drift and the legitimate corrections alike, including the live one: `0.13.0+umbrella.0.13.0` and `0.14.0+umbrella.0.14.0` name an umbrella version that was never released (#2757), and fixing those headings edits a dated section without changing what shipped in it. Sections match on the driver version alone so that correction does not read as one release deleted and another added. Replayed against the real history, the check reports the original drift at the commit that introduced it. An unresolvable base -- shallow clone, unfetched ref -- is reported and skipped rather than failed, since a checker that blocks every PR in a fresh clone is claiming a problem it never found (#2727)

## [0.14.0+umbrella.0.12.1] - 2026-08-24

### Added

- **`specfuse lint` refuses a convergent work unit that cannot act on its own declaration.** #2652 asked whether the loop should host spec authoring at all or forbid it and redirect to the authoring skills. **Support it, and refuse only the misconfigured case**: forbidding would not stop the work happening, it would only lose the loop's record of how it was done — the artifact the methodology exists to produce — and would split a project into tracked and untracked halves, silently ending cost, escalation and LEARNINGS coverage for half its real output. `check_convergent_wu_wiring` ERRORs on a unit declaring `iterate_on_failure` with no `oracles` set (a retained tree is only useful if the next attempt can see what the validator now reports; without one the unit iterates **blind** and compounds, which is strictly worse than the discard it opted out of) and on `iterate_on_failure` alongside `max_attempts: 1` (one attempt has no second pass to continue into, so the flag is a no-op its author did not intend). **ERROR rather than WARN** on `check_closing_guard_literals`' own rule — the signal is structural, not a prose match — and satisfiable on a populated tree: measured 2026-08-22, zero existing work units declare the field, asserted by a test that runs the check over every real feature folder rather than recording the measurement in prose. `done` units are skipped as sealed history. The check **returns** its findings rather than printing them, so they reach `errs` and actually fail the lint; an ERROR that prints without failing is the defect shape recorded as `[meta/six-bug-sweep/detecting-a-condition-is-not-handling-it]` (#2652)

- **Convergent work units can now iterate instead of restarting.** For a unit whose oracle is a strict whole-tree validator, a failing gate usually means the attempt is *incomplete*, not *wrong* — opposite responses, and the driver only implemented discard, so three attempts were three independent restarts and everything each one learned was thrown away (#2641). Opt in per unit with `iterate_on_failure: true`: a failed attempt that **lowered** the validator's declared `FINDINGS: <n>` count keeps its working tree, and the next attempt continues in place. Feedback needs no new plumbing — a unit's `oracles` set already runs pre-dispatch on **every** attempt and injects its output into the prompt, so pairing the flag with an `oracles` entry naming the same validator opens each attempt with current findings. That is why #2641's original proposal — replaying the rejected diff into the next prompt — is **deliberately not implemented**: re-running the validator is current rather than stale, already formatted, and immune to `truncate_failure_note`'s 200-line/8000-char budget, which would have shredded a multi-file diff and made the feature look shipped while not working. **Convergence is measured, never inferred**: the count comes from the validator, because a raw failure count is not comparable across attempts when the tree differs, and guessing from one is the proxy-reading recorded as `[meta/six-bug-sweep/detecting-a-condition-is-not-handling-it]`. An attempt with no metric falls back to discard rather than retaining a tree nobody has measured. **A non-improving attempt is rolled back to the best tree seen**, so a worse iteration cannot destroy a better one — the per-attempt reset's original purpose (bugs #71/#74) kept rather than abandoned — and two non-improving attempts running escalate `convergence_plateau`. The retry directive now branches: telling a session its work "was DISCARDED" when the tree is still there would make it re-author from scratch, the exact opposite of iterating (#2650)

- **A work unit's attempt ceiling is now configurable, per unit and per project.** `MAX_ATTEMPTS = 3` was a module constant with no override at any scope. `resolve_max_attempts` reads a unit's own `max_attempts` frontmatter first, then the project's `defaults.max_attempts` in `verification.yml`, then the constant. **Both directions of the knob matter, and #2641 only stated one**: `1` suits a unit whose shape is unknown before dispatch, so a failed pass reaches a human instead of paying twice more to rediscover the same wall — the reporting feature spent $29.30 across six attempts where `1` would have capped it near $7 — while a unit iterating against a convergent oracle wants far more than 3, since under retention (#2650) each attempt is an *iteration* rather than an independent restart, and eleven schema files plus two dozen registrations will not converge in three. A malformed value is a configuration error naming the unit, **never a silent fallback**: `max_attempts: 0` quietly becoming 3 would run a unit its author meant to run once, and a typo quietly becoming 3 would hide the typo forever. `bool` is rejected explicitly, since it is an `int` subclass and a stray `true` would otherwise mean "one attempt". The value is resolved once per unit and used at all 16 runtime sites that previously read the constant, so the attempt counter an operator sees (`attempt 2/10`) matches the ceiling actually in force (#2651)

- **The `/draft-feature` decision registry: a feature's design decisions are now recorded, cited and lint-enforced.** Ships a per-feature `DECISIONS.md` register plus the two lints that make it load-bearing rather than decorative — a citation check, so a work unit asserting a decision must point at the entry that made it, and an override check, so a later unit contradicting a recorded decision has to say so explicitly instead of silently reversing it. Filed follow-ups 1 and 3 are discharged by the same change (FEAT-2026-0058)

- **`specfuse replay-spin` answers "would the driver have caught this?" from artifacts already on disk.** Reads `events.jsonl` plus the persisted attempt notes, re-derives each attempt's `(failure_class, failure_signature)` with the current checkout's parser, and reports recorded against replayed side by side — the cheap counterpart to re-running an escalation at full price. A recorded `('other','no_gate_marker')` whose replay names a real signature is flagged, because `detect_spinning_signature_repeat` ignores that sentinel, so while a gate produced it the early halt could not fire at all — the shape #2557 fixed for hyphenated gate names. The halt is located at the first repeating signature and only spend *after* it counts as avoidable, since the attempt that trips the detector is already paid for (#2657)

### Fixed

- **The driver's resume command ran a different build than the halt came from.** The `driver_staleness_detected` halt hardcoded `resume_command=f"specfuse run --feature {id}"`, but in a checkout carrying its own source — every contributor's tree, and this repository's own dogfood — `specfuse` resolves to the pipx-installed build, so following the driver's own instruction resumed against different code than the halt came from. The driver already knew: `build_provenance.out_of_tree_warning` detects exactly that condition and prints "Run instead: python3 -m specfuse.loop.loop", so one half of the driver emitted a command the other half warned against. `resume_command_for` now reads that same source rather than restating a contradicting literal — module form in a source tree, console script outside one — and a test asserts the two cannot drift. Silent rather than loud, which is the danger: the resumed run looks normal, so a gate can be verified against stale driver code and reported green. Observed resuming FEAT-2026-0058 against installed 0.12.1 with a 0.13.0 checkout carrying four driver fixes merged the same day (#2642)

- **A scaffold version guard printed "Update specfuse to continue" and then continued.** `auto_sync` detected that the working tree's `.specfuse/VERSION` was newer than the installed scaffold, printed that line, and `return`ed — which exits `auto_sync`, not the run — so `main()` called it as a bare statement and dispatched anyway against the older scaffold. The stated contract was not the implemented one, and a version guard that proceeds is not a guard. It now raises `ScaffoldVersionSkew`, which `main()` turns into a non-zero exit naming both versions, `pip install -U specfuse`, and the `--no-autosync` override. The skew is not cosmetic: `.specfuse/VERSION` gates templates, rules and the closing-requirement surfaces a close ceremony reads, so a close under a stale scaffold can assert against obligations that have since changed. **The existing "refuses without exit" contract is preserved rather than reversed** — that test pinned that `auto_sync` must not `sys.exit`, a library function declining to kill the process, and a typed exception the caller converts honours it exactly; three existing tests were updated at the new boundary keeping each one's guarantee (no downgrade, no re-init, operator still told which version is ahead). Observed on the same incident, where the line was read as a refusal while the driver was alive, holding the lock, and about to dispatch a terminal close (#2643)

- Guard-refusal attempt-outcome events (`closing_deliverable_missing`, `deliverable_missing`, `no_deliverable_files`, `learnings_not_staged`) now populate `failure_excerpt` with the failing assertion's own summary instead of always recording `null` — a refused attempt previously retried with no more information than the attempt before it had (#2504)

- **The driver-restart cap counted restarts rather than progress, so a productive gate was escalated as a spin.** `FeatureProvider._advance` states the rule in its own docstring — *"restart me" is only progress if something changed* — and then incremented its counter on every `driver_restart` halt without checking whether anything had. A gate whose work units each legitimately edit a driver module (complete, halt so a fresh process can observe the edit, hand off to the next unit) therefore tripped `MAX_DRIVER_RESTARTS` on its third unit however much work it had finished. Observed on FEAT-2026-0058 (#2616): the `driver_staleness_detected` payloads — the same detail the guard was already holding — recorded `wu_id` differing and `remaining_wu_ids` shrinking monotonically at every step (`[T02, T03]` → `[T03]` → `[G1-CLOSE]`), with T01, T02 and T03 all reaching `done`. The gate stalled one unit from its close, and the escalation asked a human to choose between three options all premised on a spin that never happened — "split the work unit so it stops re-editing the driver", when three *different* units had each edited it once. The counter now resets when the halt detail shows the gate advanced, so the cap means what the docstring says. **The genuine spin still escalates** — one unit re-editing the driver every attempt produces an identical halt detail, which is read as no progress — and **absent evidence is not read as progress**: `_find_restart_detail` returns `{}` when the halting event cannot be re-read, and `driver_invoke` is explicit that such a run is still a restart, so a detail carrying no `remaining_wu_ids` keeps counting toward the cap rather than resetting it. Resetting there would make the cap unreachable exactly when the driver is least legible (#2617)

- **A failing gate whose name contains a hyphen was reported as though no gate had failed at all.** The marker is emitted with the gate's raw name (`f"### {gate['name']}: FAIL"`) but parsed with `^### (\w+): FAIL`, and `\w` excludes `-`. **16 of this repository's 20 configured gates are hyphenated** — every bats suite, `leak-scan`, `plan-lint`, `roadmap-link-gate`, `arm-sweep-gate` among them — so most of the gate set was structurally incapable of ever being named as the cause of a failure: the search missed and the function fell through to `('other', 'no_gate_marker')`, the sentinel meaning *no gate reported failure*. Observed on FEAT-2026-0058/T01 (#2541), where the real failure was `### sync-scaffold-symlinks-bats: FAIL`: the attempt note rendered `PASS` headers with the fault buried thousands of lines below, the retry received nothing actionable, and the unit burned **$4.96 against a $4.00 planned budget** across three attempts before escalating `spinning_detected` — the third attempt plausibly one bats fix from done. Every gate name across the shipped verification files is `[A-Za-z0-9_-]`, so the class now matches the emitter rather than widening by one character. Same family as #2390: the verdict layer blind to a failure shape, degrading a precisely-named fault to an unactionable `other`. **A second collapse, which the marker fix exposes rather than causes, is fixed alongside it**: `other`-class gates had no `_SIG_PATTERNS` entry and fell to the first-informative-line heuristic, which keys off the `$ <command>` echo the emitter writes as the first line inside the fence — a string byte-identical across every failure of a given gate, so two genuinely different faults produced one signature and could false-fire `spinning_signature_repeat`. A bats TAP pattern (`^not ok \d+ (.+)$`) now names the failing case, and the command echo is skipped on the same reasoning #167 applied to bare fences. Unreachable before this fix, because those gates never matched the marker at all. Replayed against the real attempt-3 output: `('other', 'no_gate_marker')` became `('other', 'vendor records a baseline so a later local edit is detectable')` (#2557)

- **`emit_escalation` was documented as idempotent but filed a duplicate issue on every run.** `_find_existing_issue` passed the whole correlation marker — `<!-- specfuse:escalation id=… -->` — as the `gh issue list --search` term. GitHub's issue-search tokenizer never matches a raw HTML comment, so the query returned zero rows against a queue that demonstrably held five copies of the same escalation, the find-then-create seam fell through to `gh issue create`, and the `needs-human` queue grew by one issue per run: **10 open issues for 2 real escalations**, with the genuine ones buried under the copies. The cost is not the row count — the queue is the operator's inbox, and an inbox that repeats itself stops being read. The search now sends the quoted correlation ID, a term GitHub actually tokenizes. **The exact-marker body check is retained and is load-bearing, not belt-and-braces**: a token search for `feature-FEAT-2026-0058` also returns its `-g1` child, so widening the term without that filter would trade duplicate issues for the worse failure of silently reusing the wrong one — verified against the live queue, where the parent resolves to its own issue and the child to its own. `GitHubBackend.on_feature_complete`, which this seam's docstring says it mirrors, uses `gh pr view <branch>` — a direct lookup with no tokenizer — and is unaffected. Existing coverage stubbed the runner to return a match regardless of the search term sent and never asserted the argv, so zero recall against the real API was invisible to the suite; `tests/test_escalation_dedup_search.py` now pins what `--search` actually carries (#2548)

- **`tsc` / `vue-tsc` compile failures reported `NO VERDICT FOUND` and `failure_class: other` instead of the compiler diagnostics.** `select_gate_report_lines`'s verdict pattern covered unittest, pytest, coverage, ruff and Maven surefire, but not TypeScript: `tsc --noEmit` prints no summary line in either direction — a clean run is silent, a failing run emits one `file(line,col): error TSxxxx: message` line per diagnostic with no trailing count — so the selector pinned nothing, fell back to a positional tail, and appended its `NO VERDICT FOUND` banner even though the failure carried an exact file/line/message for every one of its 15 errors. Observed on a downstream Vue/TypeScript project, FEAT-2026-0033/T02: two wasted attempts (~$2.03) retrying blind against a signature naming the command rather than the fault, then a `blocked_human` escalation pointing at nothing actionable. `_VERDICT_RE` now recognises `error TS\d+:`, the same shape as #723 (ruff) and #1413 (Maven surefire) (#2390)

- **Abandoning a work unit silently stranded every WU that depended on it, and the driver then reported the gate as complete.** `ready()` treats only `done` as a satisfied dependency, so a WU depending on an `abandoned` sibling could never become ready — the closing sequence (which every substantive WU feeds into) went stranded for the rest of the feature's life while the driver fell through to the gate-completion path and printed `Gate N complete (retro, lessons, docs, plan-next)` with none of it having run, flipping the gate to `awaiting_review`. The driver now refuses to declare a gate complete while any WU besides `done`/`abandoned` remains — halting with the stranded WU ids instead of announcing a closing sequence that never ran. (#2396)

- **Triage's `question` category routed to `needs-human` but never applied the `needs-human` label, so `/attention` could not see it.** `apply_triage` projected one label per decision, and for `question` that was `triage-question` alone — an agent's "a human must decide this" verdict was the one thing the human-facing inbox never received. `labels_for` now projects both for `question` and exactly one for every other category, deliberately: labelling triaged bugs or features `needs-human` would drown the queue this fixes. Both write paths and the marker-label repair detector go through it, so an already-marked `question` issue missing the label is returned `needs_repair` and heals on the next pass rather than needing a manual relabel (#2705)

- **`specfuse run` could not start at all in a squash-merge repository.** A squash commit is not an ancestor of the branch it was produced from, so under a pull-request-per-change squash-merge policy every feature branch falls behind its base on every merge, and `ensure_feature_branch`'s catch-up replays the squashed change against the branch's own version of the same files — conflicting **by construction** rather than incidentally. The driver raised `FeatureBranchError` and stopped, and no operator action fixed it: the prescribed `git merge <base>` is the command that had just failed, so following the instruction reproduced the refusal — the same self-defeating-remedy shape this guard already shipped once with `git rebase <base>`. A conflicting catch-up now aborts the merge, warns naming the condition and the manual recovery, and **proceeds on the branch**. That restores the reasoning recorded directly above it, which #2186 had established and this refusal contradicted: falling behind is "the normal life of a feature branch, not a fault", and refusing one is "a deadlock generator rather than a safety property". Bringing the branch up to date was a convenience, so failing at it must not be fatal; the conflict is real and still has to be resolved, but at the pull request, where a human is present. Every guarantee the refusal carried is kept — the merge is aborted so the tree is clean for the next squash commit, and git's own report still reaches the operator (#2556)

- **A run halted for a driver restart read as an idle gate, so a stopped feature looked like one nobody had started.** The halt deliberately marks nothing -- it flips no work-unit status and leaves the gate `open`, which is what let it ship with zero consumer migration, and equally what made it invisible: on disk a halted feature is an active feature, an open gate and pending units. `events.jsonl` is the only place it is recorded, so neither `/attention` nor `gate-status` said the useful thing, and `gate-status` said a wrong one -- that the gate *would* continue if the loop were re-run, when the loop had already run and stopped on purpose waiting for exactly that. Both skills now detect the halt (last event `driver_staleness_detected` with `payload.halted: true` and no later `attempt_outcome`) and report the triggering unit, the undispatched units, and the resume command. `/attention` ranks it first, because clearing it costs one command the driver has already written out. The stamped `payload.resume_command` must be printed **verbatim** rather than reconstructed: it resumes the build the halt came from, and in a checkout carrying its own source `specfuse` resolves to the installed build instead -- #2642 from the reading side, and a drift guard asserts both skills say so (#1042)

## [0.13.0+umbrella.0.12.1] - 2026-08-17

### Added

- **The conductor triaged the escalation issues it had just filed — four items of churn in one run.** `specfuse-agent` filed four `drafting-needed` escalations for undrafted queue entries and then spent four more items of the **same run** classifying those four issues: **8 items attempted, 0 units of work** (2026-08-15, issues #2380–#2383). `TriageProvider.advertise` filtered on one condition, `already_structured`, with no notion of an issue the agent itself authored — yet an escalation carries `needs-human` plus one of `escalation.CATEGORY_LABELS`, written by `escalation.py` and by nothing else, so it is **categorised by construction**. That the re-derivation carried no information is measurable: four near-identical generated bodies came out three `triage:feature` and one `triage:question`, the classifier reading a template rather than a report. `advertise` now skips any issue carrying a category label, keyed on `CATEGORY_LABELS` itself so a category added later is covered without a second list to maintain (a subtest per member asserts it). **`BugsProvider` already carried this rule from the other side** — `_HUMAN_OWNED_LABELS`, whose comment records the bug lane "trying to 'fix' its own 'PR was declined by the merge guardrails' report" — so this is the same lesson applied to the lane that does the labelling. **The escalations themselves are correct** and are not suppressed: an undrafted queue entry genuinely needs a human until FEAT-2026-0050 lands; what is removed is the second item spent re-labelling a category the issue already had. Second churn-on-own-output path found the same day — #2316 was the same shape by a different route, fixed in #2321 (#2384)

- **A verification report may no longer call a failure "pre-existing" without citing the commit it was measured on.** Twice on 2026-08-12, an agent-authored PR reported a large pre-existing failure baseline that did not exist and reasoned from it: #1876 claimed "113 pre-existing errors" and coverage "88%, below the repo-wide 90% floor" on a branch measuring **3118 tests OK at 93%** — converting a passing gate into an accepted failure — and #2028 claimed "2 failures / 110 errors, identical to the pre-fix baseline (diffed test-by-test)" on a branch with zero of either, asserting a comparison that could not have happened. `main` measured green on the same days. **This is the one output that corrupts the checking itself**: everything else the lane produces is checkable against the repo, but a false verification section is what the checking is read from. "Pre-existing" is a claim about a **different commit**, and nothing observed on the branch establishes it, so the verification skill and `result-contract.md` now require the command and the commit — typically the merge-base — with the measured numbers from both sides, and make an unmeasurable baseline a `blocked` / `could_not_proceed` outcome rather than an asserted number. The environment-shaped origin is named where a session will read it: a mass of errors sharing one signature (network refused, unresolvable pip build dependencies, a sandbox denying a socket) is a report about **where the suite ran**, not about the repository — re-run outside the restriction and say so, as PR #1907 correctly did in the same environment. **This fixes the dangerous half deliberately.** The issue separates the environment producing false failures from the session labelling them pre-existing without measuring; the second survives any fix to the first, because a session that will call an inconvenient failure pre-existing is unreliable in every environment, and a citation requirement makes the false claim unwritable regardless. **The neutral-substrate placement is a hand-off, not an omission**: the same constraint belongs in `verification-discipline.md`, which this repository vendors *from* the methodology core (`scripts/sync-scaffold.sh`'s `CORE_FILES`) and must not edit locally — a test asserts that file stays untouched, so a later quiet edit fails rather than silently diverging from core (#2075)

- **`/learnings-suggest`'s top clusters could be artefacts that outrank every genuine finding.** §2 grouped records by the raw `(failure_class, failure_signature)` tuple with no filter, so records whose signature carries no information — a bare ` ``` ` fence being the observed case — formed the largest buckets in the scan while meaning nothing. Raising `--min-wus` to cut the noise lost the real findings first: in the reporting repository the genuine cluster sat at #5, below two artefact buckets covering 41% of non-passing attempts. §2 now excludes non-informative signatures before grouping, **deferring to the driver's own `_is_noninformative_signature`** rather than restating fences/whitespace/ANSI as a second copy — a second copy of this definition is what let the two surfaces disagree in the first place — and reports the exclusion count in the run header so a thin candidate list is distinguishable from a poisoned scan. The cluster key itself is unchanged; #1977's own finding is that "the clustering itself is fine; it is being fed a degenerate key". **The driver half of #1977 was already shipped and is not re-fixed here**: `parse_gate_failure_signature` has skipped fences, whitespace and pure-ANSI lines since #169 (2026-07-20), which `git merge-base` confirms is an ancestor of v0.11.0 — the exact version the report names. That fix cannot unwrite history, and this skill reads history, so a repository that ran a pre-#169 driver keeps its poisoned rows permanently; the skill now says so, so finding fence signatures in old data is not re-filed as a driver bug. Measured in this repository: 75 non-passing `attempt_outcome` rows, exactly 1 fence signature, dated a month before the fix, and none after (#1977)

- **`specfuse lint` now warns when an `auto` feature's closing work unit names the one lessons destination `close-i` forbids.** Under `autonomy_default: auto`, `assert_learnings_staged_under_auto` refuses a closing WU that appends to `.specfuse/LEARNINGS.md` — lessons stage to `LEARNINGS-pending.md`. Observed live — PR #1784 was labelled `ci-not-green` while its checks were `SUCCESS` and it was `MERGEABLE`. `pr_ci_conclusion` now polls until every check has a conclusion or a **10-minute** deadline expires (`CI_WAIT_SECONDS` / `CI_POLL_SECONDS`; `sleep`, `clock`, the deadline and the interval are all injectable), and distinguishes **"CI has not finished"** from **"CI finished and was not green"** — a distinction the single read could not draw and the reason it mislabelled. **A settled PR still costs exactly one call**, so nothing pays for the wait unless there is something to wait for, and the fail-closed contract is unchanged: an untrustworthy read, disagreeing conclusions, or checks still pending at the deadline all still yield `unknown`, which is never `success`. The blast radius was the whole run, not the one provider: `_select_next` iterates every provider's `advertise` with **no per-provider guard**, so the exception propagated out of selection and ended the run, taking the healthy bugs, triage, answered-escalation and findings providers with it. **Every shipped behaviour of the command was reachable only by passing `--features-root` explicitly.** `read_feature_summaries` now normalises its argument at the boundary, so it accepts a `str` or a `Path` and returns an empty result for an absent directory rather than raising — a compatible widening of a public name. The reason no test caught it is worth stating: every existing test injected a fixture `Path`, so the shipped default was the one input never supplied; the new tests exercise the **default** rather than a supplied value, including a `default_providers()`-wide advertise sweep and a `_select_next` survival check. **Not fixed, and still reachable:** the un-guarded `advertise` loop itself, and the equally un-guarded `provider.reconcile()` call — a future provider that raises for a different reason will still end the run (#1746)
- **A deliverable-presence refusal now leaves a diagnostic attempt note instead of a single line the retry prompt already printed.** When a work unit failed the `produces:` presence gate, `work/<WU>/attempt-N.md` held only `assert_declared_deliverables`' one-line summary — the same string the next attempt is handed as its retry reason. Separately, `persist_attempt_notes` now terminates the last line of every note it writes. **This is why the issue reported a 0-byte file**: the note carried 43 bytes with no trailing newline, and `wc -l` counts newlines, so it read as `0`. Not included, because it needs a change to `execute_unit_attempt`'s return contract rather than a bug fix: the agent's own final message, which the issue also asked for (#1412)
- **A `produces:` path containing a literal `[...]` segment is no longer misread as a glob character class.** `assert_declared_deliverables` classified an entry as a glob whenever it contained any of `*`, `?`, `[`. Every file-based routing convention — Next.js App Router, Remix, SvelteKit — spells a dynamic route segment as a literal `[id]` directory on disk, but to `glob`/`fnmatch` that is a character class meaning "one character, `i` or `d`", so `glob.glob('src/app/api/jobs/[id]/approve/route.ts')` returned `[]` **however the file was actually spelled on disk**. The presence gate refused the work unit on every attempt with a byte-identical error and spun it to `spinning_detected`, burning three dispatches on a check that could never pass. There was no workaround inside the frontmatter contract: the only escape was to stop declaring the path in `produces:` at all. Both enforcement surfaces move together: the post-squash driver guard and the pre-squash `specfuse lint --closing` mirror, which would otherwise keep prescribing the false phrase for cents-cheap in-session feedback. The genuine no-op route is untouched — a session that really found nothing generalizable still writes the phrase (#1419)

An absent root is **created**, not refused — a first-ever run has no session-env directory, and treating that as failure would halt every clean machine (#1414)
- **Gate-verdict pinning now recognises Maven surefire failures.** `select_gate_report_lines` pinned recognisable pass/fail verdicts (unittest, pytest, coverage, ruff) ahead of a gate command's tail, but had no pattern for surefire: its `Tests run: N, Failures: M` summary and `<<< FAILURE!`/`<<< ERROR!` per-test markers sit above the final `[ERROR] Failed to execute goal ...` block, which names no failing test, so every surefire failure pinned nothing and fell back to that content-free tail — costing one feature two attempts and $7.58 before an operator diagnosed it by hand. ### Breaking

- **`escalation.webhook` is renamed to `escalation.webhook_env` in `.specfuse/agent-policy.yml`, and its value is now an environment-variable NAME rather than a URL.** An incoming-webhook URL is a bearer credential — anyone holding it can post to the channel — and `agent-policy.yml` is a committed file; `lint_monitoring`'s credential-key pattern (`key|token|secret|password|credential|connection_string`) does not match `webhook`, so nothing previously stopped an operator pasting a live Discord URL into git. **The old spelling is now an `ERROR: unknown 'escalation.webhook' key`** — rejected, not warned about and not silently accepted — so a policy carrying it fails the `agent-policy-example-lint` gate. ### Breaking

- **`specfuse-lint --closing` gains a new blocking finding, `close-l` (terminal closes) / `close-intermediate-f` (intermediate ones).** A close whose gate carries a `GATE-NN-CRITERIA.md` now fails the closing lint once per untrustworthy entry: a `kind:` missing or outside `criteria_state.ORACLE_KINDS`, a `state:` missing or outside `criteria_state.CRITERION_STATES`, or an entry whose oracle has no knowable scope (`kind: broad`) reading `state: pass` with an `attempt:` that is not the current one — a broad oracle's green can never be carried forward. A `narrow` entry's `pass` from a prior attempt is deliberately not a finding; that carry-forward is the point. The requirement is declared in `closing_requirements.py` and gated on `applies_when: criteria_artifact_present`, so a feature with no artifact lints exactly as it did before — but the driver now seeds that artifact on every close dispatch, so the gate opens as soon as a driver carrying this change is running, and from that point a close session must record a `kind:` and a `state:` for every acceptance criterion in its gate or its closing lint is red. - **The driver can now stop a run mid-gate, and it exits with a new status code, `3`.** When a work unit's squash commit touches the driver's own importable surface (a `.py` file under `specfuse/loop/`, excluding `specfuse/loop/data/`) and the gate still has work units pending, the driver halts before dispatching the next one instead of dispatching into a process whose `sys.modules` holds the pre-edit code. **Any downstream project whose gate edits the driver now needs two invocations where one used to complete the gate**, and any script, CI job, wrapper or scheduler reading the driver's exit status sees a value that did not exist before — `0`, `1` (budget and escalation halts) and `2` (unarmed drafts) were the whole vocabulary, and a caller treating "non-zero" as "failed" will report a failure for a run that stopped deliberately and lost nothing. **Nothing is lost and nothing needs repairing:** the halt flips no gate status and no work-unit status, so the gate stays `open`, every remaining unit stays `pending`, and the unit that triggered it is already `done` with its `task_completed` event written. The message names the offending unit, every driver path it touched, every work unit left pending, and the exact command to resume with; stop the driver, start a fresh process, re-run that command, and the run picks up at the unit it was about to dispatch. Expect it once per driver-editing gate. A `--dry-run` never halts, and a driver edit by the gate's *final* unit never halts because nothing is left to dispatch. - A `produces:` entry that is a directory is now an ERROR in `specfuse-lint` and refused before dispatch, instead of after a full session. The driver already refused it correctly, but only post-session and three times over — $6.42 and 20.6 minutes observed on a real feature for a `Path.is_dir()` call on static frontmatter (#593)
- An unterminated frontmatter block is now a lint finding naming the missing `---`, instead of a traceback blaming an arbitrary body line. A file the parser cannot read no longer makes its whole feature folder unevaluable by every check (#306)
- The scaffold-upgrade merge gate no longer returns a false halt against a package-era target. It invokes the packaged linter when the target ships no `.specfuse/scripts/lint_plan.py` shim, skips non-feature directories, and reports an unrunnable linter as its own blocker instead of blaming every feature by name (#309)
- CI now runs every gate `.specfuse/verification.yml` declares. `scripts/smoke-test.sh` derives its list from that file instead of carrying a hand-maintained copy, which had drifted six gates behind — including two that shipped with features and had never been executed (#592)

## [0.9.1+umbrella.0.9.1] - 2026-08-04

### Fixed

- `specfuse init` now seeds a root `CHANGELOG.md`, and `specfuse upgrade` creates one when absent without touching an existing file. Without it, the first feature in a fresh project carrying any consumer-visible change failed `close-k` at its terminal close, on a file the scaffold never created (#575)
- `sync-scaffold.sh` halts instead of silently reverting a local edit to a core-vendored file. It records each vendored file hash, so core moving forward is a fast-forward while a loop-local edit stops the run with the file named and the edit intact (#581)

### Breaking

- `scripts/bump_version.py` now requires `--umbrella-version`: cutting a release without naming the umbrella version that ships this driver is refused before any file is written, because `pipx upgrade specfuse` resolves through the umbrella package and a driver version nobody can install is half a release (FEAT-2026-0064/T03)
- New `close-k` closing requirement: a close whose "Consumer-visible contract changes" section names a real change now fails pre-squash unless `CHANGELOG.md`'s `Unreleased` gained an entry tracing to that feature's FEAT-ID — and because `specfuse init` does not create a root `CHANGELOG.md`, **a downstream project inherits the check before it has the file, and must add one** (FEAT-2026-0064/T02)
- New `close-j` closing requirement: `close-discipline.md` §2 gains a required per-entry `kind:` on the hedged-verdict follow-up record, from the closed set `acceptance-discharged` / `externally-verifiable-later` / `routed-finding` / `inherent`. **A hedged close that passed before now fails the lint.** Unhedged closes (`verdict: met`) are unaffected. The record's entry format is now machine-read — `**kind:** \`value\``, entries split on `### ` — so a record written as a YAML block or with `kind:` unbackticked lints as *missing* rather than *differently formatted* (FEAT-2026-0059/T01)
- The `event-type-gate` verification gate widens from one field to the whole envelope. It keeps its name and its `verification.yml` entry, but a downstream project whose `events.jsonl` carries any envelope violation — not just an unknown `event_type` — starts failing a gate that previously ignored it (FEAT-2026-0073/T02)
- A new `roadmap-link-gate` in `.specfuse/verification.yml`'s `code` set. **A downstream project whose roadmap already carries ERROR-severity link rot starts failing a gate it did not previously have.** Intended: the rot is real, bidirectional, and was invisible (FEAT-2026-0034/T02)
- A new `arm-sweep-gate` in the same set, reporting which arm-predicate branches have been observed on real input. Fails only when the sweep cannot evaluate a baselined feature, never on an unexercised branch (FEAT-2026-0063/T02)
- `scripts/bump_version.py` now requires `--umbrella-version`: cutting a release without naming the umbrella version that ships this driver is refused before any file is written, because `pipx upgrade specfuse` resolves through the umbrella package and a driver version nobody can install is half a release (FEAT-2026-0064/T03)
- New `close-k` closing requirement: a close whose "Consumer-visible contract changes" section names a real change now fails pre-squash unless `CHANGELOG.md`'s `Unreleased` gained an entry tracing to that feature's FEAT-ID — and because `specfuse init` does not create a root `CHANGELOG.md`, a downstream project inherits the check before it has the file, and must add one (FEAT-2026-0064/T02)

### Added

- `/diagnose-issue` skill: reads a harvester finding and the component source it implicates, and posts a structured root-cause diagnosis carrying machine-readable `confidence` and `fix_scope` fields. Shipped on all three skill surfaces (FEAT-2026-0041)
- `specfuse.monitor.diagnosis` — new public module. `Diagnosis`, `render`, `parse`, `DiagnosisParseError`, `FIX_SCOPES`. Its `<!-- specfuse:diagnosis … -->` marker is a **wire contract**: FEAT-2026-0042 parses it, so its shape cannot change silently (FEAT-2026-0041/T01)
- `specfuse.monitor.diagnose_cli` — headless diagnosis entry point, invoked as `python3 -m specfuse.monitor.diagnose_cli`. No console script added; the module path is the interface (FEAT-2026-0041/T03)
- `specfuse.monitor.autofix` and `specfuse.monitor.autofix_state` — the autofix decision layer and its GitHub-held rate-limit state (one attempt per fingerprint, daily cap). Fires headless `fix-bug` only when a diagnosis is confident and `fix_scope: small`, behind a per-component `autofix` dial that defaults to `"off"`. **Nothing fires on a schedule** — the entry point is deliberately not a console script and not a `specfuse-monitor` subcommand (FEAT-2026-0042)
- `fix-bug` gains a documented headless mode: every interactive halt maps to a named outcome, so an automated caller gets a verdict rather than a hang. Its refusal paths become a second guardrail behind the autofix predicate (FEAT-2026-0042/T03)
- `specfuse/loop/lint_roadmap.py` — reads `roadmap.md` and `roadmap-archive.md` as one link graph and checks blocked-by resolution, ref resolution in both directions, anchor adjacency, cross-file ID uniqueness, and row-versus-section status agreement, the last added by issue #465 (FEAT-2026-0034)
- `specfuse/loop/arm_sweep.py` — reports which arm-predicate verdict branches have been observed on real input, excluding features that structurally cannot be evaluated (FEAT-2026-0063/T01)
- `schemas/driver-event.schema.json` — a driver-local event registry packaged into the scaffold, sanctioning driver event types the vendored orchestrator envelope has no concept of, resolved by fall-through on a deep copy so the vendored schema on disk is never touched (FEAT-2026-0060)
- The same registry gains a `correlation_id` surface — `closing_names` and `hygiene_suffix_pattern` — so the envelope accepts the closing-sequence `G<n>-<NAME>` and hygiene `TNNH` ID shapes `correlation-ids.md` documents. **285 validation errors across 38 feature folders went to zero** (FEAT-2026-0073/T01)
- `auto-fix-attempted-failed` joins `LABEL_REGISTRY`, provisioned by `specfuse init` / `upgrade` like every other declared label (FEAT-2026-0042/T02)
- `/accept-hedged-close` now prints a **verdict-ceiling headline before any entry detail** — "no in-repo rework can raise this verdict" versus "rework exists: `<named condition>`" — computed from the entries' `kind:` values, and prompts each `routed-finding` for a tracking surface (FEAT-2026-0059)
- `CHANGELOG.md` and `specfuse/loop/changelog.py`: a Keep-a-Changelog-shaped release-notes document and the parser that reads it back, classifying entries into added/changed/fixed/breaking and requiring each to carry a FEAT-ID or issue-number trace. (FEAT-2026-0064/T01)
- `specfuse/loop/changelog.py` gains `stamp_release`, `append_entry` and `split_version_field`: cutting a version stamps `Unreleased` with the version, the date and the umbrella version — packed into the heading's version field as `<version>+umbrella.<umbrella>` so the Keep-a-Changelog heading stays one schema-legal line — opens a fresh empty `Unreleased` above it, and refuses any append or re-stamp targeting a released section (FEAT-2026-0064/T03)
- `.specfuse/release.yml`: optional release configuration holding `tag_prefix` and the `version_sources` list, read by `scripts/bump_version.py` with this repository's values as the fallback, so a project installing the scaffold sets its own release conventions instead of inheriting ours (FEAT-2026-0064/T03)

### Changed

- `specfuse.monitor.redaction._redact_text` → **`redact_text`**: promoted from module-private to public API so diagnosis prose routes through the same redaction boundary as failure artifacts rather than duplicating the secret patterns. `redact_artifact` is unchanged (FEAT-2026-0041/T01)
- `budget_projection` and the per-gate budget brake now read a work unit's **lifetime** spend rather than its current dispatch cycle, so a re-armed unit is no longer invisible to either. Measured under-read on a real feature: $6.23 and $5.01 (FEAT-2026-0062)
- `decision_class_paths` recognises non-Python dependency manifests — `pom.xml`, `build.gradle`, `Cargo.toml`, `go.mod`, `Gemfile`, `*.csproj`, `composer.json` — and reports `not_evaluable` rather than `clean` on a manifest it cannot parse. A stop class that reports clean on unreadable input is worse than an absent one (FEAT-2026-0061)
- `validate_event.load_validator()` widens the vendored envelope on a deep copy; the packaged schema file is never modified, so a vendor sync cannot silently revert the fix; the mechanism arrived with FEAT-2026-0060 and was extended here (FEAT-2026-0073)
- `close-discipline.md` §3 now requires the close ceremony to append its consumer-visible enumeration to `CHANGELOG.md`'s `Unreleased`, classified and carrying the FEAT-ID, and states that this is the same material §3 already demands rather than a second write; an `n/a` close appends nothing. The rule ships in the scaffold, so every project that upgrades inherits the obligation (FEAT-2026-0064/T02)
- `fix-bug` gains a mandatory pre-PR step: append one `Unreleased` entry carrying `#<issue-number>`, in the same commit as the fix — bugs have no close ceremony, so this is the bug side's only collection point and four of the nine PRs merged 2026-08-03/04 would otherwise have been dropped (FEAT-2026-0064/T02)

### Fixed

- A gate's FAIL report now contains the failure. `select_gate_report_lines` pins any verdict line found before the positional tail, with an explicit elision marker, and states `NO VERDICT FOUND` rather than presenting unrelated trailing output as the failure. Measured cost of the defect: two attempts, 1350 seconds, $5.31, escalated as spinning with no diagnosis; shipped as a direct bug fix in PR #322 (FEAT-2026-0068)
- `auto_archive_feature` no longer swallows the following feature's `<a id>` anchor when moving a section to the archive (#314)
- The pre-flight baseline probe no longer blames the integration branch for a **resumed** gate's failure, and no longer prints its own changeset as "proof the feature's tree matches its integration branch" — a diff that refuted the sentence above it. Remediation now points at the branch, with `git log -S<signature>` named; fixed in PR #473 (#360)
- A detail section whose `**Status:**` disagrees with its roadmap row is now an ERROR. Twenty-one of forty-two archived sections carried the disagreement when the check was written; repaired in PR #464 and guarded in #468 (#465)
- Tests no longer shell out to `python3 -m pytest`, which is a dependency of nothing in this repository and absent from CI — five instances across three features passed locally and failed only on the runner. `tests/test_no_pytest_subprocess.py` guards against a sixth (#519)
- The all-gates-passed poll no longer writes `PLAN.md status: complete`, a value absent from the valid-status vocabulary (#280)
- `lint_plan`'s bare-root-path warning and the driver's in-diff cross-check no longer disagree on how a repo-root deliverable must be spelled, fixed in PR #279 (#259)
- Stamping a release no longer produces a CHANGELOG that fails its own parser. `stamp_release` opens a fresh empty `Unreleased` and `parse_changelog` flagged every empty section, so cutting any release emitted a document failing its own parse test (#562)
