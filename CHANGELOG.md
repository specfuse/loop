[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) shape: an
`Unreleased` section collects entries as work lands, and each release heading
stamps a version and a date once one is cut.

Every entry is classified `added` / `changed` / `fixed` / or `breaking`, and
carries a `FEAT-YYYY-NNNN` or `#<issue-number>` trace back to the
retrospective or issue that explains it. `specfuse/loop/changelog.py` parses
this document against that schema; it is not free-form prose.

## [Unreleased]

### Breaking

- **`specfuse-lint --closing` gains a new blocking finding, `close-l` (terminal closes) / `close-intermediate-f` (intermediate ones).** A close whose gate carries a `GATE-NN-CRITERIA.md` now fails the closing lint once per untrustworthy entry: a `kind:` missing or outside `criteria_state.ORACLE_KINDS`, a `state:` missing or outside `criteria_state.CRITERION_STATES`, or an entry whose oracle has no knowable scope (`kind: broad`) reading `state: pass` with an `attempt:` that is not the current one — a broad oracle's green can never be carried forward. A `narrow` entry's `pass` from a prior attempt is deliberately not a finding; that carry-forward is the point. The requirement is declared in `closing_requirements.py` and gated on `applies_when: criteria_artifact_present`, so a feature with no artifact lints exactly as it did before — but the driver now seeds that artifact on every close dispatch, so the gate opens as soon as a driver carrying this change is running, and from that point a close session must record a `kind:` and a `state:` for every acceptance criterion in its gate or its closing lint is red. Nothing in this change fills those entries in; that is the close session's own work (FEAT-2026-0056)
- **The driver can now stop a run mid-gate, and it exits with a new status code, `3`.** When a work unit's squash commit touches the driver's own importable surface (a `.py` file under `specfuse/loop/`, excluding `specfuse/loop/data/`) and the gate still has work units pending, the driver halts before dispatching the next one instead of dispatching into a process whose `sys.modules` holds the pre-edit code. **Any downstream project whose gate edits the driver now needs two invocations where one used to complete the gate**, and any script, CI job, wrapper or scheduler reading the driver's exit status sees a value that did not exist before — `0`, `1` (budget and escalation halts) and `2` (unarmed drafts) were the whole vocabulary, and a caller treating "non-zero" as "failed" will report a failure for a run that stopped deliberately and lost nothing. **Nothing is lost and nothing needs repairing:** the halt flips no gate status and no work-unit status, so the gate stays `open`, every remaining unit stays `pending`, and the unit that triggered it is already `done` with its `task_completed` event written. The message names the offending unit, every driver path it touched, every work unit left pending, and the exact command to resume with; stop the driver, start a fresh process, re-run that command, and the run picks up at the unit it was about to dispatch. Expect it once per driver-editing gate. A `--dry-run` never halts, and a driver edit by the gate's *final* unit never halts because nothing is left to dispatch. There is deliberately **no opt-out flag**: an opt-out is a control a human can forget, which is the failure mode this whole feature exists to remove (FEAT-2026-0075)

### Added
- **`docs/glossary.md`, shipped into every project as `.specfuse/docs/glossary.md`.** Defines the words Specfuse uses in the order a reader meets them — roadmap, feature, gate, work unit, verification, LEARNINGS; draft, arm, dispatch, attempt, close, wrap; every status a feature, gate and work unit can hold; the four close verdicts and what "hedged" means; and the terms that genuinely are jargon (oracle, `produces:`, hollow pass, spinning, re-arm, escalation). One or two sentences each, naming the skill or command that acts on the thing where one exists. This is the surface `human-output.md`'s "keep the words the methodology is made of" rule depends on: those terms are the domain and are not going away, so they need one place that defines them rather than an inline gloss every time. The rule now points here instead of asking each skill to re-explain. Linked from `docs/README.md`; `specfuse init` and `upgrade` write it alongside the other seeded docs (#1047)
- **`specfuse.loop.learnings_query` and `specfuse.loop.upgrade_merge_gate` are now importable modules shipped in the wheel.** Both existed only as repo-local scripts under `.specfuse/scripts/`, which `init_specfuse` never writes — so the three skills calling them (`/draft-feature`, `/pick-feature`, `/scaffold-upgrade`) named a path that does not exist in any scaffolded project. Both were consumer-facing all along: the skills run against a target project, and `upgrade_merge_gate._lint_command` already branches on a "package-era" target where no shim exists. `learnings_query` is invoked as a CLI — `python3 -m specfuse.loop.learnings_query "<query>" --top N` — and `upgrade_merge_gate` as an API (`collect_reports`, `decide`), which is how each is actually used. Neither gets a console script or a `specfuse` subcommand: a subcommand needs an entry in the umbrella's `DELEGATED_COMMANDS`, and these are helpers agents call rather than commands a human types. The `.specfuse/scripts/` shims remain, re-exporting the package modules exactly as `loop.py` and `gate_eval.py` do, so this repository's dogfood path and pre-package-era targets are unaffected (#1076)
- **`.specfuse/rules/human-output.md`, a new binding rule seeded into every project and @-imported from `.claude/CLAUDE.md`.** It governs the language and length of everything a human reads — skill output, status reports, pick lists, confirmations — where `operator-escalation.md` binds only when work stops for a decision, leaving the other 90% of output with no rule and each skill inventing its own register. Five rules: answer before derivation; short by default with a named "more on request" line rather than pre-emptive detail; domain words instead of storage field names, with a translation table (`blocked_human` -> "stopped — needs you", `awaiting_review` -> "waiting for your review", `met_locally` -> "goal met, but not proven beyond this repo", and six more); every printed command runnable as pasted; and say what happened, including when it went badly. **Naming the next command or skill is explicitly endorsed, not discouraged** — the rule constrains the form of a command, never whether to offer one. An upgrade adds one `@`-import line to `.claude/CLAUDE.md` (#1047)

- `specfuse/loop/prerun.py`, a new importable module shipped in the wheel. `run_pre_dispatch(wu, feature_dir, cfg)` resolves a work unit's `prep` and `oracles` set names against `verification.yml` and runs them — `prep` fail-fast in declared order with a distinct `PREP_HALT_CLASS`, `oracles` capture-all — by calling `_run_gate_set` rather than reimplementing gate execution. An unknown set name returns a named CONFIGURATION ERROR mirroring `verify()`'s `extra_gates` phrasing, never a silent pass. Additive as an import path: nothing previously occupied it. The driver calls it on every dispatch — see the behaviour change under Changed (FEAT-2026-0057)
- `specfuse/loop/prerun_capture.py`, a new importable module shipped in the wheel. `format_oracle_capture(results)` turns captured oracle output into a prompt section bounded by `ORACLE_CAPTURE_BUDGET_BYTES` (8000, reused from `truncate_failure_note`'s existing budget for the same class of injected content), splitting the budget evenly across oracles, selecting retained lines through `select_gate_report_lines` rather than a positional tail, and marking any truncation with the exact byte count dropped. An `oracles` entry is informational while `select_gate_report_lines` is a pass/fail verdict selector, so its `NO VERDICT FOUND ... Run the command directly.` banner is stripped from every captured block regardless of size — see the entry under Fixed (FEAT-2026-0057)
- The `verification` skill documents the `prep` / `oracles` work-unit frontmatter contract, in both the plugin-shipped and vendored copies — both keys resolve against `verification.yml` set names and both run before dispatch — with a table and a choosing rule against `extra_gates`, which runs at exit (FEAT-2026-0057)
- `specfuse/loop/criteria_state.py`, a new importable module shipped in the wheel. It defines what a per-criterion close-state entry is and nothing else: `ORACLE_KINDS` (`narrow`, `broad`), `CRITERION_STATES` (`pass`, `fail`, `unverified`), a `CriterionStateEntry` record carrying `criterion_id` / `criterion` / `oracle` / `kind` / `state` / `proved_at_sha` / `attempt`, `parse_criteria_state` and `render_criteria_state` (which round-trip, and yield `None` for a missing field rather than raising), and `criterion_id_for(wu_sub_id, ordinal)`. Side-effect-free — it writes no files and decides nothing. Additive as an import path; nothing previously occupied it (FEAT-2026-0056)
- **A `GATE-NN-CRITERIA.md` artifact now appears in every `close` and `close-intermediate` session.** `precreate_dispatch_skeleton` seeds it into the feature folder at dispatch from the gate's substantive work units' acceptance criteria, extracted through a new `extract_wu_criteria` helper hoisted out of `build_autoclose_debt_enumeration` so both sites share one parser. Every seeded entry reads `state: unverified` with `oracle`, `kind`, `proved_at_sha`, and `attempt` absent, for the close's own session to fill in. Re-seeding is additive: a recorded entry is never rewritten, a criterion that appeared since the last seed is appended, and a criterion no longer produced by any work unit is left in place rather than deleted. Still a no-op for `plan-next` and every other work-unit type. Anything that enumerates a feature folder's contents will see the new file (FEAT-2026-0056)
- `criteria_state.criteria_filename(gate_n)` and `criteria_state.CRITERIA_FILENAME_RE`. The criteria artifact's basename was an f-string literal in three places — once in `loop.py` and twice in `lint_closing.py` — and now has one home before a fourth reader is added. `criteria_filename(1)` returns `GATE-01-CRITERIA.md` and `criteria_filename(12)` returns `GATE-12-CRITERIA.md`; `CRITERIA_FILENAME_RE` matches those basenames and deliberately does not match `GATE-NN.md`, `GATE-NN-REVIEW.md`, or `RETROSPECTIVE.md`. The literal was never a documented contract; the helper and the pattern are, so a downstream consumer constructing or matching that filename by hand should switch to them (FEAT-2026-0056)
- `criteria_state.build_reverification_worklist(entries, current_attempt)`, returning a frozen `ReverificationWorklist` with `carry_forward`, `reverify`, and `oracle_groups`. This is where the feature's central policy lives and it is the surface to read to answer "what is my close allowed to skip?": an entry carries forward only when its `kind` is `narrow` **and** its `state` is `pass` **and** both `oracle` and `attempt` are non-empty. Everything else re-verifies — a missing or unrecognised `kind`, `state: fail`, `state: unverified`, and every `broad` entry regardless of the attempt it was proved on, because a broad oracle has no knowable scope and a carried-forward green would be an unsound coverage claim. Unclassifiable entries fail safe into `reverify` rather than raising. `oracle_groups` collapses byte-identical oracle commands among the re-verify set so a command shared by several criteria is one line of work. Pure — no file, process, or environment access (FEAT-2026-0056)
- `loop.format_reverification_worklist(wu, feature_dir)`, which renders that partition into a dispatch's session prompt. Returns the empty string for any work-unit type other than `close` / `close-intermediate`, when the gate's `GATE-NN-CRITERIA.md` is absent, and when it parses to zero entries — a close dispatched into a gate with no recorded state gets no section rather than an empty one (FEAT-2026-0056)
- `specfuse/loop/driver_edit.py`, a new importable module shipped in the wheel. It answers one question — does a set of changed paths edit the driver's own modules — and nothing else. Public surface: `DRIVER_MODULE_PREFIXES` (the tuple `("specfuse/loop/",)`), `diff_edits_driver(paths)` returning `True` when any path falls under a prefix, `driver_paths_in(paths)` returning just the matching paths in input order, and `changed_paths_for_commit(sha, repo_root)` returning a commit's touched paths via `git show --name-only`. The first two are pure; only the last shells out. Detection keys on a commit's actual diff and never on a work unit's `produces:` or `produces_driver_helper` declarations, because those are author-supplied and the lint on the latter is WARN-only, so a unit can edit `loop.py` while declaring nothing. The module deliberately does not import `specfuse.loop.loop`, which imports it. Additive as an import path: nothing previously occupied it (FEAT-2026-0075)
- **A new warning line every driver run may now print.** When a work unit's squash commit touches a path under `specfuse/loop/`, the driver immediately prints a block beginning `STALE DRIVER PROCESS: <WU-ID> edited the driver itself (<paths>).`, stating that this process cached the pre-edit modules at import time, that every work unit dispatched next — including any close — will execute the old code, and that a fresh driver process is required before any close can verify the change. It is emitted from the outcome path right after the squash, while an operator can still act on it. Warn-only: nothing blocks, refuses, or fails. Anything that scrapes or asserts on driver stdout will see a new line class (FEAT-2026-0075)
- **A new gate-completion summary block.** At gate completion, before the gate flips to `awaiting_review`, the driver prints `STALE DRIVER PROCESS (gate summary):` followed by one line per driver-editing work unit in the gate and, when any exist, a line naming the units this same process dispatched after the earliest such edit — each of which executed the pre-edit modules. Rendered by the new `loop.format_driver_staleness_summary(edits, dispatched_after)`. A gate containing no driver-editing unit stays silent. This is the gate-end counterpart to the immediate warning above, not a replacement for it: it exists so a close reads the fact instead of reconstructing it from `ps` output and `started_at` timestamps (FEAT-2026-0075)
- **A new event type, `driver_staleness_detected`**, added to `event_types` in `specfuse/loop/data/schemas/driver-event.schema.json` and emitted at gate completion alongside the summary above. Its payload names the driver-editing units, the driver paths each touched, and the IDs of the units dispatched afterward. Every downstream project's `events.jsonl` may now carry it, so any consumer that enumerates event types — or validates events against a pinned older copy of the schema — must accept it (FEAT-2026-0075)
- Two new public helpers on `specfuse.loop.loop`: `format_driver_staleness_warning(wu_id, driver_paths)` and `format_driver_staleness_summary(edits, dispatched_after)`. Both are pure formatters and both return the empty string on empty input, so silence on a non-driver-editing unit or gate is a property of the formatter rather than of its call site (FEAT-2026-0075)
- Two new public names on `specfuse.loop.loop` for the mid-gate halt described under Breaking: `format_driver_restart_halt(wu_id, driver_paths, remaining_wu_ids, resume_command)`, a pure formatter returning the empty string on empty `driver_paths` — the same edge contract `format_driver_staleness_warning` already has — and `HALT_REASON_DRIVER_RESTART = "driver_restart_required"`, the sanctioned name for the two-invocation split. The halt is a name on the halt, not on a work unit: no work-unit status, feature status or gate status is added, so `VALID_TYPES`, `VALID_STATUS`, `MODEL_BY_TYPE`, `EFFORT_BY_TYPE`, `GATES_FOR_TYPE`, `CLOSING_ASSERTIONS_BY_TYPE` and `POST_PASS_INVARIANTS_BY_TYPE` are untouched and no consumer needs teaching new vocabulary (FEAT-2026-0075)
- **Five new keys in the `driver_staleness_detected` payload**, emitted from a second site: the halt, in addition to the gate-completion summary that first introduced the event type. A halt-emitted event carries `wu_id`, `driver_paths`, `halted: true`, `reason: "driver_restart_required"`, `remaining_wu_ids` and `resume_command`; the gate-completion site's payload (`edits`, `dispatched_after`) is unchanged. **A consumer of this event must now branch on `halted` rather than assume one payload shape.** No schema edit was required — the vendored envelope validates both shapes as-is (FEAT-2026-0075)
- `specfuse/loop/driver_edit.py` gains `is_driver_module_path(path)` and `DRIVER_DATA_PREFIXES = ("specfuse/loop/data/",)`. `DRIVER_MODULE_PREFIXES` is unchanged. See the narrowing under Changed for what this does to the two existing predicates (FEAT-2026-0075)

### Changed
- **`learnings_query`'s default LEARNINGS path now resolves against the current directory instead of the module's own location.** It was `Path(__file__).resolve().parent.parent / "LEARNINGS.md"`, which resolved correctly only while the module sat in `.specfuse/scripts/`; from inside the installed package the same expression points into site-packages, so every consumer project would have queried a file that is not theirs. It is now `Path(closing_requirements.LEARNINGS_PATH)` — `.specfuse/LEARNINGS.md` relative to the working directory, the way every other driver module locates project state — and resolved per call rather than bound at import, so it follows the process's cwd. `--file` is unchanged and still overrides it. **Anything importing `_DEFAULT_LEARNINGS_PATH` should switch to the new public `default_learnings_path()`** (#1076)
- **Eleven human-invoked skills no longer end their output with the RESULT block.** `/pick-feature`, `/gate-status`, `/arm-gate`, `/abandon-feature`, `/block-feature`, `/adopt-feature`, `/draft-feature`, `/unblock-wu`, `/learnings-curate`, `/feature-conversion` and `/accept-hedged-close` emitted it unconditionally, so every interactive run ended in a fenced slab of `status:` / `acceptance_criteria:` / `evidence:` that nothing read — `result-contract.md` calls the block "the agent-to-driver interface", and the driver parses it from a dispatched work-unit session's stdout, not from a slash command. Each skill now gates it on a non-interactive run and points an interactive one at `human-output.md`; the contract states the audience rule once, in the one place the skills defer to. **`fix-bug` is deliberately untouched** — its headless RESULT is consumed by `autofix_invoke.classify_outcome`, and `test_result_block_audience` guards both directions: every listed skill states the condition, and `fix-bug` still does not. Anything scraping a skill's interactive output for a `result` block will stop finding one; a driver- or headless-invoked run is unchanged (#1047)
- **Skill prose that told the operator to run `loop.py` now says `specfuse run`.** Nine references the `.specfuse/scripts/` sweep did not reach, because they name the module bare rather than by path — `/adopt-feature`'s "the human runs `loop.py` when ready", `/pick-feature`'s own skill description, `/unblock-wu`'s write-ordering note, and six more. References that locate driver *source* for the agent — `fire_terminal_flips` in `loop.py`, `lint_plan.py`'s output — are deliberately left, since they point at code rather than instruct the reader (#1047)
- **Skills no longer print `python3 .specfuse/scripts/*.py` as the next command — they print `specfuse run` / `specfuse lint` / `specfuse monitor-lint`.** 25 references across 11 skills. `init_specfuse` never writes `.specfuse/scripts/`; it is a dogfood shim tree in this repository's own checkout, so in a scaffolded project every one of those commands failed on a missing path — `/pick-feature` handed the user a three-command chain of them. This is the same defect `test_gate_commands_reference_no_missing_scripts` has guarded for `verification.yml` since the pip-install work, on a surface that guard never covered; `TestSkillsNameRunnableCommands` now covers it, on both the canonical and vendored skill trees. Two helpers with no packaged equivalent (`learnings_query.py`, `upgrade_merge_gate.py`) are exempted by name with a pointer to #1076 rather than silently matched. Anything asserting on a skill's printed next-command sees new text (#1047)
- **`specfuse upgrade` now backfills rule imports a project's `.claude/CLAUDE.md` is missing, instead of leaving it on the rule set it was scaffolded with.** `_write_claude_md` returned early whenever the sentinel `@.specfuse/rules/result-contract.md` was present — which correctly stopped it clobbering a project's own file, but also meant a rule added after a project was scaffolded shipped into `.specfuse/rules/` and was **never loaded there**. Missing imports are now inserted directly after the last rule import already present, so the block stays contiguous, `rules-local` imports and surrounding prose keep their position, and a file already carrying every line is returned byte-identical. Idempotent, and it still never appends the block header twice. **An upgrade now modifies `.claude/CLAUDE.md` in cases where it previously did not** — the diff is added `@`-import lines only (#1047)
- **`operator-escalation.md` now separates required content from required length.** The six parts and the feature briefing are unchanged as *content*; what changed is delivery. What this is about, the decision, the options with their one-line trade-off, and the recommendation stay in full; the state so far and why it did not close automatically compress to a sentence each; per-work-unit narration, event excerpts, and full cost reconciliation are held back behind a closing line that names them, so the reader can ask for exactly the part they want. Requested by the operator on user feedback that escalations, while much improved, were still longer than the decision needed. Compressing is not omitting — a brief that drops the trade-offs or the recommendation is called out as useless rather than concise (#1047)
- **Every command reference in the shipped scaffold, docs and skills now names a `specfuse` subcommand instead of a flat `specfuse-*` script.** `specfuse-loop` -> `specfuse run`, `specfuse-lint` -> `specfuse lint`, `specfuse-monitor` -> `specfuse monitor`, `specfuse-monitor-lint` -> `specfuse monitor-lint`, `specfuse-stats` -> `specfuse stats`. This reaches consumer projects: `verification.yml.example` seeds its plan-lint and monitoring-lint gates with the subcommand form, the `specfuse-monitor.yml` GitHub Actions template runs `specfuse monitor run --runner gh-actions`, and `WU.template.md`, `close-discipline.md`, the docs tree and the skills all say `specfuse lint --closing`. **Nothing breaks on upgrade**: the flat names keep working as aliases from the umbrella until 1.0.0, with identical arguments and behaviour, and this package still declares them in `[project.scripts]` — an existing project's hand-authored `verification.yml` is untouched and keeps running whatever it already says. Projects should migrate their own gate commands when convenient; `specfuse doctor` lists which flat names are still on PATH, and `SPECFUSE_NO_DEPRECATION_WARNING=1` silences the alias notice in a noisy hook or CI job (#1047)
- **`specfuse init` / `specfuse upgrade` now seed a single `Bash(specfuse:*)` permission instead of `Bash(specfuse-loop:*)` and `Bash(specfuse-lint:*)`.** One entry authorises the whole suite, including subcommands the scaffold never enumerated (`specfuse monitor`, `specfuse stats`). The settings merge is additive as it always was, so a project wired before this keeps both legacy entries — they still authorise the deprecated flat aliases — and simply gains the new one; nothing is revoked and no approval is re-prompted. A freshly initialised project gets only `Bash(specfuse:*)`, so a repo that pins or asserts on the old two entries in its own tooling should widen that assertion (#1047)
- **The driver-staleness predicate is narrowed to the importable surface, so a path that produced a warning before produces none now.** `driver_edit.diff_edits_driver(paths)` and `driver_edit.driver_paths_in(paths)` were a bare `str.startswith(("specfuse/loop/",))`; both now delegate to the new `is_driver_module_path(path)`, which additionally requires the path to end in `.py` and to *not* fall under `DRIVER_DATA_PREFIXES = ("specfuse/loop/data/",)`. Concretely, `diff_edits_driver(["specfuse/loop/data/schemas/driver-event.schema.json"])` returned `True` and now returns `False`, and the same flip applies to every file under `specfuse/loop/data/` — docs, templates, schemas, example configs, workflow files, and a hypothetical `.py` scaffold payload under `data/`, which is excluded by the data-prefix condition even though it ends in `.py`. The rationale is that a data file is read from disk at runtime and never enters `sys.modules`, so editing it cannot make a running driver stale; the module's own docstring already claimed "the driver's own importable surface" and the prefix was broader than the claim. Measured across this repository's 90 gates, 3 of 42 flagged gates go silent. This matters more than it did when the predicate was warn-only: the same predicate now decides whether to stop a run (see Breaking above), so a false positive costs a halted gate rather than a spurious line. **Any consumer that imported these helpers to answer "does this diff touch the driver directory" now gets a different answer for data paths and should use its own prefix test** (FEAT-2026-0075)
- **A pristine seeded entry is no longer a `close-l` / `close-intermediate-f` finding**, narrowing the blocking lint described under Breaking above. As first shipped, an entry carrying `state: unverified` with no `kind:` and no `oracle:` — exactly and only what the driver's own seeding writes — was a finding, one per acceptance criterion of every substantive work unit in the gate. Because the driver seeds that artifact on every close dispatch, every `close` and `close-intermediate` in every project would have begun with a red closing lint from the moment a driver carrying the change was running (41 findings on the feature that introduced it), with nothing shipped to fill them in. The check now skips an entry no close has annotated, on the grounds that there is nothing yet to have gotten wrong. **Any deviation re-enters scope immediately** — a `state` other than `unverified`, or a recorded `oracle`, means a close has begun touching the entry and every original rule applies again — and the soundness rule is untouched: a `broad` entry reading `state: pass` with an `attempt:` that is not the current one is still a blocking finding. The consequence to review is that the lint no longer enforces "every criterion was verified", only "everything you claimed about a criterion is well-formed"; a close may now legitimately leave an entry unannotated and lint clean, so its honesty about what it did not verify rests on its deferred-verification list rather than on the linter (FEAT-2026-0056)
- **The per-attempt untracked-file cleanup gains a permanent, driver-wide carve-out.** `_clean_attempt_untracked` never unlinks a file whose basename matches `criteria_state.CRITERIA_FILENAME_RE`, joining the single pre-existing carve-out for `events.jsonl`. Without it the artifact was deleted between attempts of the same close — it is created inside the attempt loop while the untracked-file snapshot is taken once per work unit outside it, so a failing attempt's reset saw it as "appeared since the snapshot" and removed it, wiping recorded state on exactly the multi-attempt runs it exists to serve. **The carve-out applies to every feature in every project after upgrade, not only to features using this artifact**: any file named `GATE-NN-CRITERIA.md` anywhere in the tree now survives a failed attempt's cleanup. The blast radius is bounded and asserted — an unrelated untracked file created after the snapshot in the same feature folder is still deleted (FEAT-2026-0056)
- **Every `close` and `close-intermediate` session now receives a new prompt section.** `execute_unit_attempt` appends a `## Re-verification worklist (gate N)` section to the work-unit body at dispatch, after the pre-dispatch oracle-capture section and before the agent session starts. It states the carried-forward and re-verify counts, lists each carried-forward criterion with its oracle and the attempt it was proved on, lists the grouped re-verification commands one line per distinct oracle command, and always ends with an unconditional statement that the close's own `close-discipline.md` §1 feature-level question is never carried forward and runs every attempt regardless. The prompt every close agent reads has therefore changed, in every project, on every close dispatch, whether or not that project ever annotates an entry; `plan-next` and all other work-unit types are unaffected (FEAT-2026-0056)

- **The driver now honours `prep:` and `oracles:` in work-unit frontmatter.** `WorkUnit` gains `prep: list[str]` and `oracles: list[str]`, `load_wu` parses both with the same contract `extra_gates` has (a string is coerced to a one-element list, a list is preserved, any other type raises ``ValueError: `prep` must be a string or list of strings``), and `execute_unit_attempt` calls `run_pre_dispatch` before the session is spawned, appending the formatted `## Captured oracle output (pre-dispatch)` section to the work-unit body the session receives. Two consumer-visible consequences on upgrade: a work unit carrying a `prep:` or `oracles:` key of the wrong shape now fails to load where the key was previously ignored, and `load_verification()` is now read on every dispatched attempt rather than only at verification time (FEAT-2026-0057)
- A failing `prep` entry halts before dispatch with a distinct outcome.
