# Changelog

All notable changes to this project are documented here, in the
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) shape: an
`Unreleased` section collects entries as work lands, and each release heading
stamps a version and a date once one is cut.

Every entry is classified `added` / `changed` / `fixed` / or `breaking`, and
carries a `FEAT-YYYY-NNNN` or `#<issue-number>` trace back to the
retrospective or issue that explains it. `specfuse/loop/changelog.py` parses
this document against that schema; it is not free-form prose.

## [Unreleased]

### Changed

- **Dispatched sessions no longer read every rule file before acting.** The preamble opened with "Read `.specfuse/rules/` in full": ten files, 11,573 words, fetched by tool call at the start of every session on top of the 2,461 words `.claude/CLAUDE.md` already injects, then carried in every later turn's cache read. The binding block is the contract; the preamble now says so and a session reads a further rule file only when its unit body names it, as close and plan-next bodies already do. (#3422)
- **Dispatched sessions no longer carry the skills index.** Every `claude -p` dispatch loaded the project's `.claude/skills` index into the session prompt (34 skills and 1,534 words of descriptions in this repository) although a dispatched unit invokes no skill: the narrow-tier instructions are in the preamble and unit bodies name skill files by path, for reading. The driver now passes `--disable-slash-commands`; `defaults.dispatch_skills: true` in `verification.yml` restores the index for a project whose units do call `/skill-name` in-session. (#3423)

## [0.24.0+umbrella.0.15.0] - 2026-09-25

### Fixed

- **A run that could not read the queue no longer reports `drained`.** When the snapshot's issue listing failed, the run treated it as empty, found no candidates and stopped with `drained` — exit 0, zero attempted, zero escalated — with **nine dispatchable bugs in the queue**. `drained` means "worked through everything there was"; here it meant "could not see anything", and the summary, which is the part an operator reads and the only part automation parses, rendered them identically. A nightly run whose credentials broke looked like a quiet backlog. An unreadable issue listing now refuses the run under its own stop reason `snapshot_unreadable`, following `dirty_tree`'s precedent — nothing was budgeted because nothing was dispatched — with one escalation carrying which listing failed, and a **non-zero exit** so a scheduled run's status is self-describing without its log. Outcomes, `drained` included, keep exit 0. An unreadable **PR** listing still does not refuse: `max_open_prs` deliberately declines to fire on a number it could not measure, so the run now states that the cap is unenforced for that run rather than leaving it in the log. Whether that case should refuse too is a decision, not a defect, and is left open. (#3392)
- **A judge that lowers a terminal verdict says where its findings went.** The `judged` event recorded `findings: N` with `reason: null` and named nothing. The findings were never lost — `write_judge_followups` writes each one verbatim into `FOLLOW-UPS.md` and commits it, confirmed in a consumer's own history — but a reader of `events.jsonl` had no pointer out of it. One operator searched `events.jsonl`, the feature's `work/` directory and for a repository-level judge artifact, concluded the text did not exist, and priced a third close at ~$12 to re-derive a finding sitting in a committed file. The lowered event now carries `findings_path` and `finding_criteria`, and its `reason` names both instead of being `null` on the one path where something specific was found. The finding **text** deliberately stays out of the event: it is already recorded verbatim in one place, and a second copy invites the two to disagree. (#3406)
- **Triage writes the severity label the repository actually defines.** `severity_aliases` was one-directional: the bug lane translated a repository's own words **inbound**, and triage wrote canonical words **outbound** — words that repository may never have defined. Measured on a repo labelling `critical`/`major`/`minor`: seven escalations of `--add-label triage:bug,severity:high` failing with a `gh` exit status. Worse than a failed write, because the marker is written first and succeeds, so severity **is** judged and recorded — while the lane reads severity from the **label**. Three issues came out with no severity label and two with a stale one contradicting the marker their own run had just written, and an unreadable severity fails closed against `min_severity`. So triage silently removed from the lane the very issues it had just classified for it. The projection already existed — `severity_label_projection` shipped with #3353 and was wired into the backfill's write path and only there; triage is the other writer. Both of its write sites now project, the marker still records the canonical value so it stays comparable across repositories, and the projection is derived from the same `gh label list` the rubric already read, keeping that once-per-run. (#3386)

### Changed

- **Work units whose deliverable is a validated tree get the two rules they were missing.** A repository whose deliverable *is* a spec tree runs the loop with units that author spec files, and those fail differently from code units — a consumer decomposed them the way code units are decomposed and lost $5.37 (3 attempts, `files_touched: []` on all three) and $29.30 (6 refused attempts, abandoned). Neither was an ordinary authoring mistake; both were toolchain atomicity constraints. `authoring-work-units` §6 now carries the constraint that cuts **against** sizing: where the artifact is validated as a whole, some units are indivisible regardless of size, because a `$ref` to a schema that does not exist yet breaks the bundle and there is no partial state to hand on. §9 spells out the structural assertion — enumerate the identifiers the unit declares, assert each resolves in the **regenerated** artifact, not in the files the unit just wrote. §12 refuses "no test framework" as an exemption and sends it to that substitute: exempting reads like the refactor case and is nothing like it, since nothing else is asserting the unit did its job, and it would remove the cheapest hollow-pass guard for a whole class of repository. `docs/methodology.md` §10's spec-front-end row becomes three-valued (*none* / *consumed* / *authored*) — one consumer carried the third case in ~40 lines of project `CLAUDE.md` because the row could not express it. Both rules are stated for any validated-tree deliverable, not specs alone. (#3407)

## [0.23.3+umbrella.0.15.0] - 2026-09-24

### Fixed

- **A red-on-base command that cannot run no longer reads as red.** The probe returned `code != 0`, so a shell exiting **127** (command not found) or **126** (not executable) was read as "the test failed at the base" — which *permits* the merge. Fail-open, in the one guardrail whose entire job is to be harder to satisfy than the other six. Surfaced by turning the check on for a real repository whose command is a committed script: the probe's worktree is the **base** tree, so on any PR whose merge base predates that script the file is absent, `sh` exits 127, and a test that actually passes at the base was reported as red. POSIX reserves 126 and 127 for the shell's own failure to run the command, so neither says anything about the test; both now resolve to unverified, which declines. The two declining reasons already separated "the check said no" from "the check never ran" — the exit-code reading collapsed them toward the permissive side. (#3403)

## [0.23.2+umbrella.0.15.0] - 2026-09-24

### Fixed

- **The red-on-base probe runs the operator's command through a shell.** It used `shlex.split` and no shell, so it could not express any command using a pipe, `||`, `$(...)` or an inline environment override — which is every real one. The gate commands in `verification.yml` are run with `shell=True` for exactly this stated reason, and the probe runs the same kind of operator-authored string. Caught turning the guardrail on for a Maven repository, which needs `$(...)` just to turn changed file paths into the class names `-Dtest=` accepts: enabling it there would have declined **every** merge as `red_on_base_unverified` while looking correctly configured. The command now goes to `sh -c` (through the injected runner, so it stays testable without executing anything) and each substituted path is `shlex.quote`d — unquoted, a path containing a space became two arguments and one containing `;` ended the command. The template is POSIX shell; no Windows spelling is invented. (#3400)

## [0.23.1+umbrella.0.15.0] - 2026-09-24

### Fixed

- **Three registered labels could not be created in any repository.** `gh label create` rejects a description over 100 characters with `HTTP 422 — description is too long`, and `bug-lane:ci-pending` (101), `bug-lane:test-not-red-on-base` (108) and `bug-lane:red-on-base-unverified` (125) were all over it. `provision_labels` reports the failure and carries on — right for a repository being briefly unreachable, wrong for a spec that can never be created anywhere — so `ci-pending` had been failing in every repository since it shipped, and nothing noticed because the consequence appears later and elsewhere: a declining bug-lane path applies a label that was never created, which is #1420 arriving through the one door its regression test does not watch. That test asserts every declining reason **has** a spec; a new one asserts the spec is one GitHub will **accept**. Surfaced by a real upgrade: `label provisioning — created [], failed [...]`. (#3397)

## [0.23.0+umbrella.0.15.0] - 2026-09-24

### Added

- **The bug lane can require proof that a PR's new test was red on the merge base.** Its six guardrails all measured the **form** of a PR — a test file is touched, CI is green, the diff is small, no judge path, traceable provenance, under the daily cap — and none measured whether the symptom the issue reported stopped reproducing. Audited on one consumer repository: **seven lane PRs passed all six, four were incomplete for the issue they claimed to close**, and two of those merged unattended and closed the issue behind a symptom that still reproduced. A test that passes at the merge base proves nothing about the fix — it asserts behaviour that already held, or tests something adjacent to the defect. `rules.bugs.require_red_on_base` turns the check on and `rules.bugs.red_on_base_command` declares how to run it; the probe runs in an isolated `git worktree`, never the live tree the lane is working in, and never guesses a command, because one that silently matched no tests would exit non-zero, read as red-on-base, and wave every PR through. Off by default: turning it on for a deployment that has not declared the command would decline every merge on upgrade, which is a silent automerge shutdown rather than a guardrail. "The check said no" and "the check never ran" decline under separate reasons and separate labels. Its limit is stated rather than implied — it catches "the test proves nothing", not "the test proves the wrong thing". (#3377)
- **The bug lane picks its model from what is known about the issue.** Every bug was dispatched at `sonnet`/`medium` — `build_invocation`'s defaults, never overridden — whether it was a one-line template fix or a change whose direction has architectural consequences. Of seven bugs one run dispatched, the two that produced correct fixes had issues already carrying a diagnosis naming the file and the shape of the fix; the two closed on review as wrong reported a symptom and left the fix location open. The lane now reads `fix_scope` from the `/specfuse:diagnose-issue` comment and dispatches from it: `large` gets a stronger model, `small` and `external` keep the previous profile, and an issue with **no** diagnosis is dispatched exactly as before. `rules.bugs.model_by_fix_scope` lets a deployment choose what each scope costs it, merged over the shipped defaults so naming one scope does not drop the others. Every item's detail now states what it was dispatched with and where that came from (`[dispatched opus/high via diagnosis:large]`) — without it the dial is unmeasurable, which is worse than no dial because it looks like evidence. The proposal's other half, an `effort=` field triage guesses from issue text, is deliberately **not** implemented: effort is a property of the codebase rather than of the report, and the issue that read as most mechanical in that run was the one whose correct fix required knowing where a seed value came from. (#3391)
- **`/specfuse:fix-bug` can say the direction is a decision, not only that the work is too big.** The skill had one way to decline — `refused`, keyed on size and risk — and no outcome for a fix that is small where **which** fix is correct is a decision the issue does not make. A headless session cannot ask, so it picked. Measured: a lane session made a generated service block on a soft-delete archive, reversing a decision a feature gate had explicitly recorded and making any aggregate with a child permanently un-archivable; it was coherent work with a passing test, it passed all six merge guardrails, and it reached `eligible`. `needs_decision` joins the outcome set and escalates like the other two stopping outcomes — the session opens no PR, so nothing is merged and no issue is closed behind a fix nobody chose. It is deliberately not `refused`, whose remedy is `/draft-feature`: the wrong instruction for a question whose answer is usually one line. The skill tells a session to reach for it when candidate fixes differ in **who they affect** rather than in size, and to carry the options themselves into the escalation so the operator answers a question instead of starting a diagnosis. (#3390)

## [0.22.3+umbrella.0.15.0] - 2026-09-23

### Fixed

- **FEAT-2026-0113's gate-3 `feature_oracle` asserts the milestone it declares.** The gate's Definition of done is a pair — a marked, severity-less issue re-read under `--apply` has its marker amended and the `severity:<value>` label projected **after** it, and the conductor reaches the mode not at all — but the module named as the oracle held only the second half. `T10H` removed the tracer-bullet function the first half drove and deleted the test with it; the behaviour stayed covered by a unit test, so what was lost was not coverage but the gate's own feature-level question having an asserting command. Measured: reversing the write order left the declared oracle reporting **OK**. The restored assertion drives `main()` through argv, so the listing, the classification and the write order are all inside what is measured — the difference between a feature oracle and a second unit test — and it catches both a duplicated label write and a pure ordering inversion with identical call counts. The module's docstring, which claimed the half it had stopped asserting, now says what it checks. (#3359)
- **The severity backfill reconciles a human-applied severity instead of re-deciding it.** A backfill candidate is selected on its *marker* — already triaged, no `severity=` field — and nothing looked at whether the issue already carried a `severity:*` **label**. So an issue a person had labelled was classified fresh and had a second severity label written beside theirs, with `read_severity_label` then returning whichever it recognised first: the agent silently overriding a person at the `min_severity` floor. This was masked when FEAT-2026-0113 closed, because the measured repository's scheme yielded a one-entry rubric and the classifier failed closed on exactly those issues — **shipping the default alias table (#3355) removed the mask, not the hazard.** `severity_decision` now consults the label first: labels agreeing on one value reconcile (the marker is written **from** the label, no classification session is spent, and no label is written because the label is the source), labels resolving to more than one value or carrying a word nothing can read are left alone with a stated reason, and an unlabelled issue classifies as before. Measured against the consumer repository the feature was sized on: **37 of 61 candidates already carried a human-applied severity**, every one of which the previous path would have re-decided. The run report now distinguishes reconciled from classified rows and a deliberate refusal from a classification failure, since that is what the tracked follow-up's re-run condition is read off. (#3360)
- **A failed attempt's gitignored output no longer reaches the attribution probe.** `git reset --hard` restores tracked files and leaves ignored ones in place, so the probe that decides whether a failure predated a work unit was measuring that unit's own build output — one reported run halted a **green** branch with `preexisting_gate_failure` because 11 generated files survived the reset. The mechanism already existed: #162 snapshots untracked paths at dispatch and deletes what appeared since, but `untracked_paths` runs `--exclude-standard`, so ignored paths were deliberately carved out (the driver's own `work/` notes are gitignored and must survive). `ignored_paths` is its twin, and the one reset followed by the probe now cleans what the attempt itself created. Two things bound it: the listing is `git ls-files --others --ignored`, not `git status --ignored`, which collapses a wholly-ignored directory to one entry and would have seen no change in exactly the reported case; and snapshot semantics mean a build cache present at dispatch is never touched, so the expensive-to-rebuild concern needs no configuration. `work/` is kept explicitly, since the snapshot is per-unit and attempt 1's notes would otherwise look new at attempt 2's reset. (#3330)
- **The attribution halt no longer claims nothing was dispatched.** `format_preexisting_gate_failure` was written for a gate-entry probe, where "Zero work units were dispatched for this gate" was true. FEAT-2026-0109/T01 removed that probe, leaving attribution as the **only** path that renders the message — and there a unit was dispatched, its attempt failed, and the driver reset the tree and re-ran the checks. Every fresh-gate claim was therefore false exactly when it was shown. The message now names the attributing unit, says the probe ran after its reset, and points the operator at leftover state first. The proof is softened wherever it appears: a `git diff --stat` compares **tracked** files, so it can neither see a check's gitignored inputs nor distinguish pre-existing breakage from output this feature's own failed attempt left behind — `git reset --hard` restores tracked files and leaves ignored ones in place. In the reported incident the checks failed on exactly that, and the message read as conclusive enough to cost a bisect across three commits. (#3330)

## [0.22.2+umbrella.0.15.0] - 2026-09-21

### Fixed

- **`max_items_per_day` says that it is applied per run.** The key is named for a day and enforced per run — holding it across runs needs state that survives a process, which is a feature rather than a fix — and `resolve_max_items` recorded that honestly in a docstring, which is not a surface an operator reads. A run printing `max_items=62 (policy)` against a key named `per_day` invited the reading the name suggests, and that reading is the unsafe one: a day of runs can exceed the number the operator believes they set. The opening line now reads `max_items=62 (policy per run)` — only this cap is annotated, since only this one has a name promising something wider than it delivers — and `/specfuse:derive-agent-policy` states it where the value is proposed, so the operator is told before they choose the number rather than after. This closes the last open expectation on #3340; budget resolution from policy, the `max_open_prs` gate and the effective-caps line shipped earlier. (#3340)
- **The authoring rule now teaches the reword the Do-not-touch collision warning asks for.** `lint_plan`'s WARN names its fix — reword the boundary to name the surfaces it protects rather than the file the unit also produces — but §7 of `/specfuse:authoring-work-units`, which is where an author is told to put the broken file in `produces:`, said nothing about wording the boundary. The rule generated the shape that trips the warning and gave no way to answer it, and the shape is every hygiene unit, not an edge case. §7 now shows the surface-naming wording and names the wording that actually went wrong: `FEAT-2026-0113/T08H` wrote "every other function in <module>", which read literally forbids editing the one function that unit existed to fix — it passed only because the acceptance criteria named the target unambiguously, so boundary and criteria contradicted each other and only the criteria were load-bearing. A new test pins the lint and the rule together so the recommended fix and the rule producing the shape cannot drift apart. (#3357)
- **The bug lane writes a repository's own severity word, not just its own.** `severity_aliases` (#3349) let an operator declare that `severity:major` means `high`, and `read_severity_label` honoured that map — so the `min_severity` floor read the label correctly while the classifier FEAT-2026-0113 added answered in the published vocabulary and the write path projected it straight to `severity:high`. A repository declaring aliases ended up with **both spellings in circulation** and nothing reporting the asymmetry. `severity_label_projection` now maps a vocabulary value to the label the repository actually spells it with, and `apply_severity_backfill` writes that. Two bounds keep it honest: a label the repository does not define is never projected (the shipped aliases name words like `blocker` that most repositories never created), and an in-vocabulary label always wins — the same precedence `read_severity_rubric` already applied. The marker still records the vocabulary value, so `severity=` stays comparable across repositories; only the label takes the operator's word. `read_severity_rubric` gained an optional `existing=` so the run derives rubric and projection from **one** `gh label list`, keeping the once-per-run listing intact. (#3353)
- **Published prose no longer names a downstream consumer's repository.** `/specfuse:fix-bug`'s Step 7 prose and the 0.22.1 changelog entry beside it both cited a real consumer's `org/repo#issue` while explaining the `Closes #<n>` rule. Everything under `plugins/` ships in a release, is mirrored to the umbrella marketplace and lands in every consumer's checkout; `CHANGELOG.md` ships in the pip package — a far wider surface than the commit bodies, PR bodies and roadmap prose leak-scan already guards. `leak_scan` could not catch it: a bare `org/repo#n` is indistinguishable from the many legitimate `specfuse/loop#NNNN` references the same prose uses, and a denylist entry is the wrong instrument because the name legitimately appears in `.specfuse/agent-policy.yml` (it is the repo the bug lane is pointed at) and in this repo's tests — it cannot tell published prose from local configuration. Both citations now describe the repo instead, keeping the traceable reference on this project's own issue, and a new guard holds the positive invariant: published prose may cross-reference `specfuse/*` and nothing else. (#3378)

## [0.22.1+umbrella.0.15.0] - 2026-09-20

### Fixed

- **`rules.bugs.required_checks`: the bug lane can be told which green it requires before merging unattended.** `evaluate_merge_guardrails` accepted any `success` conclusion. A repository whose PR job is deliberately a fast lane — excluding a test group that guards committed expectations — gives a `success` that **cannot fail** on that class of defect, and `automerge: "on"` merges it. Measured: a bug-lane PR left `main` **red for an hour**, all six guardrails green, caught by a human rather than the lane. The two tests it broke both carried `@Tag("regression")`, a group that repo's PR job excludes. **The assumption the fast-lane/nightly split rests on is that every change already passed the full gate set before its PR opened** — true for driver work-unit PRs, and **not** true for bug-lane PRs, where a headless session chooses which tests to run and reports the ones it chose. The new key names the check(s) that must be **present and passing**: one that never ran declines with `required check never ran: <name>`, and one that was **skipped** declines too — skipping is not a failure in general, which is why `_BUCKETS_OK` tolerates it, but a check an operator named as required and that did not run cannot establish what it was required to establish. A malformed value requires **nothing** rather than blocking every merge on a typo, and a bare string is the single-check case. Absent, behaviour is unchanged. Declines route through the existing `REASON_CI_NOT_GREEN`, with the specific check name carried into the evidence. **The issue's option (2) is deliberately not built**: inferring from a diff which tests *should* have run is a heuristic guarding an unattended merge, and "the operator named the check" is a guarantee where "we guessed the session tested enough" is not. (#3373)

- **The identical-failure breaker no longer counts `refused`, which is a per-item judgement rather than an environment fault.** #3343's breaker counted *every* escalation. Measured: a run worked 10 of 29 items — **two fixes merged, one held back on red CI, six issues correctly declined as feature-scoped** — and the breaker stopped the remaining 19, writing an escalation asserting "the cause is this run's environment" about a lane that was working. A human then had to disprove it. The distinction #3343 failed to draw: some outcomes are reached **without reading the item** (a dispatch that failed, a session that produced no outcome marker, a crash) and some are reached **by reading it** — `/fix-bug`'s `refused` says the work is not bug-sized, and `ci_not_green` / `pr_not_found` are facts about that issue's PR. Only the first kind can be environmental. `ActionOutcome` gains `environmental`, **defaulting `False` so a provider must opt in** — a provider that says nothing never trips the breaker, failing safe toward not stopping a working run. `BugsProvider` sets it from `outcome_named`, the distinction #3343 itself introduced and then did not connect. **A per-item judgement resets the count rather than being ignored**: a lane still reaching verdicts is not one whose environment is broken, so the breaker now fires only on an unbroken run of genuine faults — which is what the original 55-item incident was. (#3372)

## [0.22.0+umbrella.0.15.0] - 2026-09-20

### Fixed

- **A setup failure now stops the run after three identical failures instead of parking every item in the queue.** `run_agent` treated every item independently, which is right for an item-specific failure and wrong for one whose cause is the run's environment. Measured: a headless command that did not resolve was invoked **55 times**, producing 55 `could_not_proceed` escalation comments and 55 `needs-human` labels over 16 minutes — **one defect, in the runner's own setup, identical every time**. The blast radius is self-inflicted and sticky: `needs-human` is in `_HUMAN_OWNED_LABELS`, so the lane skips those issues from then on and a single setup defect removes the whole bug queue from automation until a human clears the labels by hand. `failure_signature` flattens per-item numbers so `issue #1916` and `issue #1915` failing the same way count as one cause — **deliberately coarse, because a signature too precise never fires**, which is the state that cost 55 escalations. At `IDENTICAL_FAILURE_LIMIT` the run stops with `run_level_failure` and records **one** escalation against `run:identical-failures`, with no `target_issue` and so no further label: the stop removes nothing more from automation. **The escalation template also stops asserting a refusal it did not establish.** `classify_outcome` fails closed to `could_not_proceed` for output naming no outcome, which covers both "the skill refused" and "the session never started" — and the template stated the first, recommending promotion to a feature. All 55 comments said so when the skill had never run; an operator following that advice would have promoted 55 bugs to features on the strength of a missing command. `outcome_was_named` carries the distinction from the session's own text through `BugLaneResult.outcome_named` to the payload, which then points at the runner's setup and says plainly that nothing about the issue is established. **The items escalated before the breaker trips keep their records** — it can only know the cause is environmental after seeing it repeat. (#3343)

- **A completed fix no longer escalates `pr_not_found` because its issue reference is in the PR title rather than the body.** `/specfuse:fix-bug`'s own `gh pr create` example put `(closes #<n>)` in the **title** while its body template opened with `Closes #<n>.` GitHub closes an issue from either, so a PR satisfying the title looks correct to a human and to GitHub — and the lane, which matched only the body, found nothing. Observed end to end: a run fixed an issue in a downstream consumer repo in 11.8 minutes — real fix, pushed branch, PR with a regression test, reported `completed` — then escalated `pr_not_found`, so **no guardrail ever evaluated finished work, nothing merged, and the escalation read as though no fix existed**. `pr_closes_issue` now takes a keyword-only `title` (defaulting empty, so a caller that predates this is unaffected) and matches either place, with the `\b` boundary that stopped `#198` matching `#1984` preserved on the new surface. **The selection side had the same blind spot and a worse consequence**: `_has_open_pr` gates "does this issue already have a fix in review", so a title-only PR answered *no* and the issue would have been dispatched a **second** time — duplicate work on an already-fixed issue. Both call sites now pass the title. `SKILL.md`'s example drops the title reference and requires the body to open with `Closes #<n>.`, giving it one canonical home; matching either is what keeps already-shipped skill versions working. (#3366)

- **`specfuse doctor` now preflights the slash commands the headless lanes dispatch, instead of nothing checking until a run.** #3342 is what that cost: the bug lane dispatched a command resolving nowhere, and the first thing to notice was the run itself — after it had dispatched 55 triaged bugs, collected `Unknown command: /fix-bug` from every one, and labelled all 55 `needs-human` for a defect unrelated to any of them. The report gains `dispatched_commands` and names any lane whose command resolves nowhere in `recommended_action`. **The dispatched set is read from each lane's own `DEFAULT_COMMAND`, not re-listed**, so a third lane is covered by adding its constant and nothing else — and that direction is the contract, since `autofix_invoke` is held to zero top-level imports by its own test and cannot import a resolver. The two failure modes are reported separately because they are different fixes: a plugin not installed, versus installed but not enabled for this project; a bare command falls back to looking for `.claude/skills/<name>/SKILL.md`. It reads files and invokes no `claude` — a preflight needing the real client to answer is not one. **A lane whose module will not import is reported rather than skipped**: the first draft swallowed that with `try`/`except`/`pass`, which would have let `doctor` report every command resolving while silently checking only one lane. (#3347)

- **Two lint messages that told an author to do something the guard could not observe.** `check_produces_satisfiability`'s overlap WARN said "Drop the path, or state the incremental edit this WU makes to it in the body" — **there is no body scan**, so following that advice changed nothing and the warning repeated forever. Worse, the one action that *does* silence it is dropping the `produces:` entry, which feeds the driver's presence and in-diff guards: understating a real contract to quiet advisory noise. ## [0.14.0+umbrella.0.12.1] - 2026-08-24

### Added

- **`specfuse lint` refuses a convergent work unit that cannot act on its own declaration.** #2652 asked whether the loop should host spec authoring at all or forbid it and redirect to the authoring skills. **Support it, and refuse only the misconfigured case**: forbidding would not stop the work happening, it would only lose the loop's record of how it was done — the artifact the methodology exists to produce — and would split a project into tracked and untracked halves, silently ending cost, escalation and LEARNINGS coverage for half its real output. `check_convergent_wu_wiring` ERRORs on a unit declaring `iterate_on_failure` with no `oracles` set (a retained tree is only useful if the next attempt can see what the validator now reports; without one the unit iterates **blind** and compounds, which is strictly worse than the discard it opted out of) and on `iterate_on_failure` alongside `max_attempts: 1` (one attempt has no second pass to continue into, so the flag is a no-op its author did not intend). **ERROR rather than WARN** on `check_closing_guard_literals`' own rule — the signal is structural, not a prose match — and satisfiable on a populated tree: measured 2026-08-22, zero existing work units declare the field, asserted by a test that runs the check over every real feature folder rather than recording the measurement in prose. `done` units are skipped as sealed history. The check **returns** its findings rather than printing them, so they reach `errs` and actually fail the lint; an ERROR that prints without failing is the defect shape recorded as `[meta/six-bug-sweep/detecting-a-condition-is-not-handling-it]` (#2652)

- **Convergent work units can now iterate instead of restarting.** For a unit whose oracle is a strict whole-tree validator, a failing gate usually means the attempt is *incomplete*, not *wrong* — opposite responses, and the driver only implemented discard, so three attempts were three independent restarts and everything each one learned was thrown away (#2641). Opt in per unit with `iterate_on_failure: true`: a failed attempt that **lowered** the validator's declared `FINDINGS: <n>` count keeps its working tree, and the next attempt continues in place. Feedback needs no new plumbing — a unit's `oracles` set already runs pre-dispatch on **every** attempt and injects its output into the prompt, so pairing the flag with an `oracles` entry naming the same validator opens each attempt with current findings. That is why #2641's original proposal — replaying the rejected diff into the next prompt — is **deliberately not implemented**: re-running the validator is current rather than stale, already formatted, and immune to `truncate_failure_note`'s 200-line/8000-char budget, which would have shredded a multi-file diff and made the feature look shipped while not working. **Convergence is measured, never inferred**: the count comes from the validator, because a raw failure count is not comparable across attempts when the tree differs, and guessing from one is the proxy-reading recorded as `[meta/six-bug-sweep/detecting-a-condition-is-not-handling-it]`. An attempt with no metric falls back to discard rather than retaining a tree nobody has measured. **A non-improving attempt is rolled back to the best tree seen**, so a worse iteration cannot destroy a better one — the per-attempt reset's original purpose (bugs #71/#74) kept rather than abandoned — and two non-improving attempts running escalate `convergence_plateau`. The retry directive now branches: telling a session its work "was DISCARDED" when the tree is still there would make it re-author from scratch, the exact opposite of iterating (#2650)

- **A work unit's attempt ceiling is now configurable, per unit and per project.** `MAX_ATTEMPTS = 3` was a module constant with no override at any scope. `resolve_max_attempts` reads a unit's own `max_attempts` frontmatter first, then the project's `defaults.max_attempts` in `verification.yml`, then the constant. **Both directions of the knob matter, and #2641 only stated one**: `1` suits a unit whose shape is unknown before dispatch, so a failed pass reaches a human instead of paying twice more to rediscover the same wall — the reporting feature spent $29.30 across six attempts where `1` would have capped it near $7 — while a unit iterating against a convergent oracle wants far more than 3, since under retention (#2650) each attempt is an *iteration* rather than an independent restart, and eleven schema files plus two dozen registrations will not converge in three. A malformed value is a configuration error naming the unit, **never a silent fallback**: `max_attempts: 0` quietly becoming 3 would run a unit its author meant to run once, and a typo quietly becoming 3 would hide the typo forever. `bool` is rejected explicitly, since it is an `int` subclass and a stray `true` would otherwise mean "one attempt". The value is resolved once per unit and used at all 16 runtime sites that previously read the constant, so the attempt counter an operator sees (`attempt 2/10`) matches the ceiling actually in force (#2651)

### Breaking

- **`escalation.webhook` is renamed to `escalation.webhook_env` in `.specfuse/agent-policy.yml`, and its value is now an environment-variable NAME rather than a URL.** An incoming-webhook URL is a bearer credential — anyone holding it can post to the channel — and `agent-policy.yml` is a committed file; `lint_monitoring`'s credential-key pattern (`key|token|secret|password|credential|connection_string`) does not match `webhook`, so nothing previously stopped an operator pasting a live Discord URL into git. **The old spelling is now an `ERROR: unknown 'escalation.webhook' key`** — rejected, not warned about and not silently accepted — so a policy carrying it fails the `agent-policy-example-lint` gate. ### Breaking

- **`specfuse-lint --closing` gains a new blocking finding, `close-l` (terminal closes) / `close-intermediate-f` (intermediate ones).** A close whose gate carries a `GATE-NN-CRITERIA.md` now fails the closing lint once per untrustworthy entry: a `kind:` missing or outside `criteria_state.ORACLE_KINDS`, a `state:` missing or outside `criteria_state.CRITERION_STATES`, or an entry whose oracle has no knowable scope (`kind: broad`) reading `state: pass` with an `attempt:` that is not the current one — a broad oracle's green can never be carried forward. A `narrow` entry's `pass` from a prior attempt is deliberately not a finding; that carry-forward is the point. The requirement is declared in `closing_requirements.py` and gated on `applies_when: criteria_artifact_present`, so a feature with no artifact lints exactly as it did before — but the driver now seeds that artifact on every close dispatch, so the gate opens as soon as a driver carrying this change is running, and from that point a close session must record a `kind:` and a `state:` for every acceptance criterion in its gate or its closing lint is red. Nothing in this change fills those entries in; that is the close session's own work (FEAT-2026-0056)
- **The driver can now stop a run mid-gate, and it exits with a new status code, `3`.** When a work unit's squash commit touches the driver's own importable surface (a `.py` file under `specfuse/loop/`, excluding `specfuse/loop/data/`) and the gate still has work units pending, the driver halts before dispatching the next one instead of dispatching into a process whose `sys.modules` holds the pre-edit code. **Any downstream project whose gate edits the driver now needs two invocations where one used to complete the gate**, and any script, CI job, wrapper or scheduler reading the driver's exit status sees a value that did not exist before — `0`, `1` (budget and escalation halts) and `2` (unarmed drafts) were the whole vocabulary, and a caller treating "non-zero" as "failed" will report a failure for a run that stopped deliberately and lost nothing. **Nothing is lost and nothing needs repairing:** the halt flips no gate status and no work-unit status, so the gate stays `open`, every remaining unit stays `pending`, and the unit that triggered it is already `done` with its `task_completed` event written. The message names the offending unit, every driver path it touched, every work unit left pending, and the exact command to resume with; stop the driver, start a fresh process, re-run that command, and the run picks up at the unit it was about to dispatch. Expect it once per driver-editing gate. A `--dry-run` never halts, and a driver edit by the gate's *final* unit never halts because nothing is left to dispatch.
